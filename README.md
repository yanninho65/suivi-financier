## 1. Modèle de données

### 1.1 Colonnes d'import (Excel/CSV, mapping par nom normalisé, ordre libre)
`Date · Montant · Type · Catégorie · Personne · Compte · Compte cible · Groupe · Remarque`

**Formats acceptés depuis l'abandon de MoneyControl Primoco en parallèle** (source désormais saisie manuellement plutôt qu'exportée d'une autre appli) :
- **Date** (`U.parseDateValue`) : vraie cellule Excel, numéro de série Excel, texte `JJ/MM/AAAA`, ou texte `JJ/MM/AA` (année 2 chiffres, pivot 68 : `00`-`68` → 2000-2068, `69`-`99` → 1969-1999).
- **Type** (`U.normType`) : accepte indifféremment l'interne anglais (`Income`/`Expense`/`Transfer`) et le français, insensible casse/accents — `revenu`, tout ce qui commence par `exp`/`dépense`, `virement`, ou tout ce qui commence par `trans`/`transfert`.
- **Montant** : nombre ou texte avec virgule décimale, signe porté directement par la valeur (positif = revenu, négatif = dépense) — pas de déduction du signe depuis la colonne Type.

### 1.2 Objet transaction interne
```
{ id, date, dateISO, montant (signé), type, categorie, personne, compte, compteCible, groupe, remarque,
  groupeBase,   // "groupe" sans le suffixe "(...)" final, ex. "Cliff Haven (23-01-08)" -> "Cliff Haven"
  transform }   // { mode: "same"|"month"|"yearsplit", year, month }
```
`groupeBase` (dérivé une fois via `U.baseGroupe()`, backfillé au chargement pour les anciens enregistrements) n'est **plus qu'un helper d'affichage/de repli** — voir §2 pour le principe central : le libellé complet (avec suffixe) est la clé de référence partout, jamais le nom de base seul.

### 1.3 Date transformée (`computeTransform()`)
Dérivée de la `Remarque` :
- suffixe `AA-MM` → transaction affectée à ce mois précis (`mode:"month"`).
- suffixe année à 4 chiffres → montant réparti également sur les 12 mois de l'année (`mode:"yearsplit"`). Partout où ce type de transaction est affiché dans un contexte de **période** (Budget, Évolution en mode "Mois transformé"), seule la part correspondant aux mois de la période est montrée, jamais le montant total d'origine.
- sinon → identique à la date indiquée (`mode:"same"`).

Ce triplet `{mode, year, month}` est calculé une fois par transaction (au chargement/import) et réutilisé tel quel par le moteur Budget (`computeGroupBudget`) et par le moteur Évolution (`buildEvolutionIndex`) — même logique de redistribution mensuelle dans les deux onglets.

## 2. Groupes de groupe / groupes de personnes

Un même lieu/séjour donne souvent plusieurs groupes datés (`Cliff Haven (23-01-08)`, `Cliff Haven (24-02)`) qu'on veut rattacher à une période de vie plus large (`Ghana`). Règles éditables à la main, jamais déduites.

### 2.1 Principe central : le libellé complet prime toujours, jamais le nom de base

Ce principe a été renforcé dans une passe de correction (deux occurrences distinctes du même nom de base, ex. "France (26-06_07)" et "France (25-07_08)", sont des groupes différents et ne doivent **jamais** se voir attribuer la même classification par accident) :

- **`findGroupAliasRule(base, full)`** (règles `groupe → groupe de groupe`) : cherche d'abord une règle exacte sur `full` (le libellé littéral complet, ex. `"France (26-06-07)"`) ; ce n'est **que** si aucune règle `full` n'existe qu'un repli sur une règle "base générique" (`groupe = nom de base, pas de full`) s'applique — et cette règle générique n'est alors utilisée que pour les occurrences **non rattachées individuellement**, jamais pour outrepasser une règle `full` existante. Il n'y a plus de fenêtre de dates sur les règles (`dateFrom`/`dateTo` retirés du modèle et de l'UI — voir §2.5) : la seule façon de distinguer deux occurrences est désormais le libellé complet lui-même.
- **`getGroupKind(fullName)` / `getGroupVoyageMonth(fullName)`** (classification Vie quotidienne/Voyage et mois d'affectation, §2.4) : indexées directement sur le libellé complet. Un repli sur le nom de base n'existe que pour lire des réglages enregistrés avant ce correctif (compatibilité ascendante) — tout nouvel enregistrement se fait sous le libellé complet.
- **`getGroupDateRange(key)`** (dates de séjour → jours/moyennes, §2.4) : indexée depuis l'origine sur le libellé complet (`editingFull || editingBase` côté UI) — n'a jamais eu ce problème.

En clair : **un nom de base seul n'est jamais utilisé pour appliquer un réglage à une occurrence précise** — il ne sert que (a) de repli de compatibilité pour d'anciennes données, ou (b) de mécanisme volontaire et explicite de "règle générique" que l'utilisateur choisit de créer via la case "Appliquer à toutes les périodes de « X »" de l'écran d'édition d'un groupe (§2.4), pour classer en bloc toute occurrence non encore rattachée individuellement.

### 2.1 bis Tri chronologique des groupes de groupe

Partout où les groupes apparaissent groupés par groupe de groupe et où un ordre chronologique a du sens — picker Groupe de la fiche transaction (§6.2), vue Groupe de l'onglet Évolution (§6.4.1), filtre Groupe de l'onglet Transactions (§4), picker Groupe d'un ajustement manuel du Budget (§6.3.6) — le classement suit `AGG.groupeHierarchyChrono(transactions)`, variante triée de `groupeHierarchyFull` : les groupes de groupe sont classés **du plus récent au plus ancien**, en se basant sur la **date de début du groupe enfant le plus ancien** de chacun ; à l'intérieur d'un groupe de groupe, ses groupes enfants sont classés **du plus ancien au plus récent** (leur propre date de début). Les groupes non rattachés à un groupe de groupe restent toujours à part (`flat`, triés par ordre alphabétique) — jamais fondus dans un groupe de groupe, jamais mélangés au tri chronologique. Le résultat porte un indicateur `preSorted:true` que les vues consommatrices respectent pour ne pas re-trier alphabétiquement par-dessus (`renderPickerList`/`nestedFilterHtml` : si `h.preSorted`, l'ordre des sections et de leurs enfants tel que fourni est conservé tel quel).

Le picker de groupe **principal/additionnel** du Budget (`groupPickerHierarchy`, §6.3.2) **n'est pas concerné** — il continue d'utiliser `groupeHierarchyFull` et reste trié alphabétiquement, comportement inchangé. Le picker de groupe d'un **ajustement manuel** (`adjustmentGroupHierarchy`, §6.3.6), lui, réutilise directement `groupeHierarchyChrono` tel quel : les deux pickers de groupe du Budget suivent donc désormais des tris différents selon leur rôle (principal/additionnel = alphabétique ; ajustement = chronologique, aligné sur la fiche transaction).

**Date de "départ" d'un groupe** (`AGG.getGroupStartDate(fullLabel, txnMinDatesMap)`), ordre de priorité strict :
1. La **date de début** configurée manuellement pour ce groupe (`getGroupDateRange`, §2.5) — toujours prioritaire quand elle existe.
2. À défaut seulement, la **date entre parenthèses** dans le libellé du groupe, interprétée par `AGG.parseGroupSuffixDate` (via `AGG.groupLabelSuffix` pour l'extraire) : `AA-MM-JJ` → jour précis (ex. `23-01-08` → 8 janvier 2023) ; `AA-MM_MM` → plage de mois sur une même année, départ = 1ᵉʳ du premier mois (ex. `24-01_06` → 1ᵉʳ janvier 2024) ; `AA-MM` → mois, départ = 1ᵉʳ du mois (ex. `22-07` → 1ᵉʳ juillet 2022) ; `AAAA` → année seule, départ = 1ᵉʳ janvier.
3. En dernier recours (aucune date configurée, aucun suffixe reconnaissable), la **date de la transaction la plus ancienne** de ce groupe précis (`AGG.groupStartDatesMap(transactions)`, calculée une fois pour tous les groupes plutôt qu'à la demande).

### 2.2 Règles (`groupAliasRules` / `personAliasRules`)
```
{ groupe, superGroupe, full? }   // groupes : "full" = libellé complet si scopé à une occurrence précise
{ personne, superPersonne }      // personnes : jamais d'occurrences datées, donc jamais de champ "full"
```
`getGroupeDisplay(t)` = super-groupe si une règle correspond (via `findGroupAliasRule`, §2.1), sinon `t.groupe` brut (libellé complet, jamais tronqué).

### 2.3 Où ça s'applique
- **Filtres** Groupe/Personne : liste imbriquée, groupes de groupe repliés par défaut, cochable au niveau du cluster ou d'un élément précis (`Filters.matches()` teste la valeur résolue **et** la valeur brute).
- **Transactions**, regroupement : le bouton **"Compte"** est désormais en première position dans les regroupements (`GROUPBY_LABEL`, §6.2). Le regroupement "Compte" utilise le **compte réel** (`t.compte`, nom exact), plus le type de compte — cf. §3, le type de compte reste disponible séparément dans l'onglet Comptes.
- **Onglet Transactions (liste)** : le libellé affiché reste toujours le **groupe littéral** (`t.groupe`, avec date), jamais le groupe de groupe résolu — affiché sur la ligne 3 de chaque transaction, cf. §6.2.
- **Onglet Évolution** (§6.4), vue Groupe : sections = groupe de groupe résolu via ce même mécanisme, items = libellé complet du groupe.

### 2.4 Écran "Gérer les groupes / Gérer les personnes"
Deux instances de `createAliasManager(cfg)` (`window.__SF_GROUPMGR` avec `hasDates:true, showKind:true`, `window.__SF_PERSONMGR` avec `hasDates:false`). Vue unique, hiérarchique (l'ancien second mode "Toutes les règles", table à plat, a été retiré — voir "Nettoyage des règles obsolètes" ci-dessous pour son remplacement).

**Vue hiérarchique — points clés :**
- Chaque **occurrence datée distincte** apparaît comme sa propre ligne, avec son **libellé complet** (date incluse) — les groupes ne sont jamais fusionnés/masqués sous le seul nom de base. Idem pour la vue "Non classés".
- Chaque ligne affiche une icône (voyage/vie quotidienne) selon le type du groupe, calculée via `getGroupKind(b.base)` où `b.base` **est** le libellé complet (`groupeHierarchyFull`, plus jamais une base tronquée).
- Position de scroll et sections `<details>` dépliées sont conservées entre deux re-rendus.

**Édition d'un groupe (tap sur une ligne) — édition par occurrence :**
Le tap ouvre un écran scopé à **cette occurrence précise** (pas à toutes les dates du même nom de base) :
- Le champ "groupe de groupe" est pré-rempli avec l'affectation qui s'applique réellement à cette occurrence (résolue via `findGroupAliasRule(editingBase, editingFull)`).
- **Enregistrer** crée par défaut une règle `full` scopée à cette occurrence précise (comparaison stricte par égalité) — sans toucher aux règles des autres occurrences du même nom de base.
- Case à cocher optionnelle **"Appliquer à toutes les périodes de « X »"** : crée/remplace alors la règle générique (sans `full`) du nom de base — c'est le seul moyen de créer une règle générique dans l'interface (§2.1).
- Si le groupe n'a pas de suffixe de date (occurrence unique, `editingFull === editingBase`), pas de case à cocher : comportement simple, règle générique directe.
- **Type de groupe** (Vie quotidienne / Voyage) + mois voyage : `key = editingFull || editingBase` — indexé sur le libellé complet, comme les autres réglages par occurrence (§2.1). Ce mois voyage (`Store.settings.groupVoyageMonth`, format interne `AAAA-MM`) n'est plus utilisé que par l'onglet Budget : il prime désormais aussi sur le **Mois calculé** partout ailleurs dans l'app (regroupement Transactions §6.2, filtre §4) — voir `AGG.getCalcMonthYM(t)` juste en dessous. Export/import Excel (§8/§7) : la colonne "Mois voyage" écrit/lit une **vraie date Excel au 1ᵉʳ du mois** (`voyageMonthToDateObj`), jamais le texte `AAAA-MM` brut — voir §8 pour le détail.

#### Mois calculé d'une transaction — `AGG.getCalcMonthYM(t)`
Fonction unique, seule source de vérité pour "à quel mois calculé appartient cette transaction", utilisée par le regroupement Transactions "Mois calculé" (§6.2), la liste des mois du filtre "Mois calculé" (§4) et le filtre lui-même — les trois **doivent** rester alignés sur cette même fonction. Ordre de priorité :
1. Si le groupe de la transaction est de type **"voyage"** (`getGroupKind`) **et** qu'un **mois voyage est renseigné** dans sa fiche (`getGroupVoyageMonth`, non vide) → ce mois-là, pour **toutes** les transactions du groupe, quelle que soit leur date réelle ou leur Remarque.
2. Sinon, si `t.transform.mode==="month"` (suffixe `AA-MM` en Remarque, §1.3) → le mois transformé habituel.
3. Sinon → le mois réel de la transaction (`t.date`).

Le mode `"yearsplit"` (répartition sur 12 mois, §1.3) n'est **jamais** éclaté ici — contrairement au moteur Budget, une transaction ne peut appartenir qu'à un seul groupe/mois à la fois dans une liste ou un filtre ; en `"yearsplit"` (ou en `"same"`), on retombe simplement sur le mois réel (règle 3), exactement comme avant l'introduction de cette fonction.
- **Dates de début/fin** (§2.5) : disponibles pour tous les groupes, quel que soit leur type, même clé (`editingFull || editingBase`).

**Sélection multiple** (bouton "Sélectionner", **Personnes uniquement** — `!cfg.hasDates`, absent côté Groupes) : coche par nom de base réel, puis "Déplacer vers…" applique une règle générique en masse.

**Nettoyage des règles obsolètes** (`obsoleteRules()`, remplace l'ancienne vue "Toutes les règles") : un bouton "N règle(s) obsolète(s) · Nettoyer" apparaît en haut de l'écran **uniquement** s'il existe des règles dont le groupe/la personne visé·e n'apparaît plus dans **aucune** transaction actuelle — comparaison insensible casse/accents (`U.normalize`) sur le nom de base, ou sur le libellé complet exact pour une règle `full`. Cliquer ouvre une confirmation qui **liste chaque règle concernée** (`base/full → super-groupe`, jusqu'à 10 affichées, "+N de plus" au-delà) avant suppression définitive. Fonction générique, partagée par Groupes et Personnes.

> **Piège pour toute évolution de `createAliasManager`** : les deux instances (Groupes/Personnes) peuvent coexister dans le DOM avec des **éléments internes de mêmes id** (`am-close`, `am-search`, etc. — le HTML de chaque sheet est régénéré à chaque ouverture mais l'ancien contenu de l'autre sheet, une fois fermée, reste présent et caché). Tout nouveau `document.getElementById("am-…")`/`document.querySelectorAll("[data-…]")` ajouté dans une fonction de rendu doit être scopé au `sheet` local (`sheet.querySelector(...)`), jamais global à `document` — sinon le mauvais gestionnaire peut être câblé silencieusement (bug réel corrigé : le bouton Fermer de "Gérer les personnes" ne répondait plus après avoir ouvert "Gérer les groupes" dans la même session).

### 2.5 Dates de début/fin d'un groupe → jours & moyennes/jour
`Store.settings.groupDateRange` : `{ [libellé complet]: {dateFrom, dateTo} }`. Saisi dans l'écran d'édition d'un groupe (tous types confondus), en dessous des autres réglages.

Dès que les deux dates sont renseignées, calcul et affichage en direct (avant même d'enregistrer) :
- **Nombre de jours** = `(dateTo - dateFrom) + 1`.
- **Revenus/jour, Dépenses/jour, Total/jour** = totaux des transactions de ce groupe précis (`t.groupe === clé`) ÷ nombre de jours.
- Si une des deux dates manque, ou si `dateTo < dateFrom` (jours ≤ 0) : aucun calcul, aucune division — message "Renseignez les deux dates…" à la place. `getGroupDayStats(key)` (exposé sur `AGG`) retourne `null` dans ces cas.

**Date de fin dynamique ("toujours aujourd'hui")** : case à cocher sous les deux champs de date, pour un groupe/séjour encore en cours dont la durée doit continuer à s'allonger sans repasser modifier la date chaque jour. Cochée, le champ "Date de fin" se grise et affiche la date du jour (lecture seule), et c'est la valeur spéciale `AGG.GROUP_DATE_TODAY_SENTINEL` (chaîne `"today"`, jamais une vraie date ISO) qui est stockée dans `dateTo` — jamais la date du jour figée au moment de la sauvegarde. Partout où un calcul a besoin d'une vraie date (`getGroupDayStats`, l'aperçu live de l'écran d'édition), `AGG.resolveGroupDateToValue(dateTo)` résout cette sentinelle en date du jour **au moment du calcul** ; `AGG.getGroupStartDate` (§2.1 bis) n'est jamais concerné, la sentinelle ne s'applique qu'à `dateTo`, jamais à `dateFrom`. Export/import Excel (§7/§8) : la sentinelle s'écrit en toutes lettres `"Aujourd'hui"` dans la cellule "Date fin (jours)" (au lieu d'une date, `isoToDateObj` ne saurait pas la convertir) et se reconnaît à la réimport (comparaison insensible casse/accents sur `"aujourd'hui"`/`"today"`, `U.normalize`) — toute autre valeur dans cette colonne est interprétée comme une vraie date via `U.parseDateValue`, comportement inchangé.

Exporté/importé avec les autres paramètres (§7). **Il n'existe plus de fenêtre de dates séparée sur les règles de groupe de groupe** (l'ancien champ `dateFrom`/`dateTo` des règles `groupAliasRules`/`personAliasRules` a été entièrement retiré du modèle, de l'UI d'édition (déplacement groupé compris), de l'export/import et de `findGroupAliasRule` — seul `groupDateRange` ci-dessus conserve une notion de dates, mais pour un usage complètement différent : les jours de séjour réels, pas une fenêtre de validité de règle).

## 3. Types de compte et acronymes
`Store.settings.accountTypes` = `{ "Nom du compte": "Courant"|"Épargne"|texte libre }`, saisie manuelle uniquement (pas d'heuristique). Compte sans type → "Courant" par défaut. Utilisé pour regrouper les comptes par type dans l'onglet Comptes (§6.1) et dans le regroupement "Compte" de Transactions (§6.2).

`Store.settings.accountAcronyms` = `{ "Nom du compte": "ACRO" }` (4 caractères max, majuscules). Réglable dans le même écran ("Types de compte", menu ☰), juste sous le type — `AGG.getAccountAcronym(compte)` retourne l'acronyme saisi, ou à défaut le dérive automatiquement des initiales du nom (`deriveAccountAcronym`, jusqu'à 3 lettres). Affiché en **bandeau vertical** sur chaque transaction dans l'onglet Transactions (§6.2) — c'est la seule indication visuelle du compte dans la liste.

## 4. Filtres

Champs, dans l'ordre du menu (`MENU_ITEMS`) : **Période, Mois indiqué, Mois calculé, Type, Compte, Groupe, Catégorie, Personne**, plus une recherche texte libre. Cumulables entre champs (AND), multi-sélection en OR au sein d'un champ. Ouverture en deux étapes (menu de catégories de filtre → liste dédiée, `sheetView`). Catégorie reste triée Revenus A→Z puis Dépenses A→Z (`AGG.distinctValuesCategorieSorted`). Groupe : groupes de groupe triés chronologiquement (§2.1 bis), pas alphabétiquement.

**Filtres actifs** : ne s'affichent plus en bandeau au-dessus de la liste Transactions — visibles **dans la sheet de filtres elle-même**, sous le menu principal (`activeFiltersSectionHtml()` dans `renderMenuStep`), **regroupés par type de filtre** (Période/Mois indiqué/Mois calculé/Type/Compte/Groupe/Catégorie/Personne/Recherche via `CHIP_KIND_LABEL`/`CHIP_KIND_ORDER`), chaque puce individuellement supprimable (`F.removeChip`, re-render local sans fermer la sheet). Seul indicateur resté sur la page Transactions : le badge numérique sur l'icône filtre du bouton flottant (§6.2, `updateFilterBadge`).

**Tout sélectionner / Aucun** : chaque section à choix multiples (Mois indiqué, Mois calculé, Type, Compte, Groupe, Catégorie, Personne — pas Période) affiche deux boutons en haut de sa liste (`quickSelectRowHtml`/`wireQuickSelect`/`selectAllForKey`/`selectNoneForKey`) : sélectionne/vide tout le champ d'un coup, indépendamment de tout regroupement visuel.

**Mois indiqué / Mois calculé** (`Filters.moisIndiques`/`moisCalcules`, valeurs `"AAAA-MM"`) : listent respectivement les mois de la date réelle et du **mois calculé** (§2.4, `AGG.getCalcMonthYM`). Affichage **groupé par année** (`moisGroupedHtml`/`wireMoisGrouped`, même pattern que Compte ci-dessous) : cliquer sur l'en-tête d'une année sélectionne/désélectionne en bloc tous ses mois — **c'est le mécanisme pour filtrer sur une année entière**, il n'existe pas de champ "année" séparé.

**Compte** : affiché **groupé par type de compte** (§3, `comptesGroupedHtml`/`wireComptesGrouped`) plutôt qu'en liste plate — cliquer sur l'en-tête d'un type sélectionne/désélectionne tous les comptes de ce type. Le champ "compte" n'ayant pas de résolution "affichage groupé" comme Groupe/Personne (pas de valeur unique représentant tout un type dans `Filters.matches`), le clic sur l'en-tête ajoute/retire directement chaque compte membre, plutôt qu'une valeur de type unique.

**Groupe / Personne** : liste imbriquée (`nestedFilterHtml`/`wireNestedFilter`), groupes de groupe/personnes repliés par défaut, cochables au niveau du cluster (ajoute la valeur résolue, `Filters.matches()` teste valeur résolue **et** valeur brute) ou d'un élément précis. **Personne** uniquement : les personnes non rattachées à un groupe de personnes apparaissent sous un en-tête dédié **"Sans type"** (`NESTED_DIM_CONFIG.personnes.noGroupLabel`), cliquable comme les autres pour tout sélectionner en bloc — mais via bascule directe de chaque membre (pas de valeur "groupe" unique pour "Sans type", contrairement aux en-têtes de groupe de personnes nommés).

## 5. Réglage global des décimales
`Store.settings.decimals` (0 ou 2) est un réglage **global**, partagé entre les onglets Transactions et Comptes — un seul bouton pilule "0,00" (`U.decimalsToggleBtnHtml`/`U.toggleMoneyDecimals`), présent uniquement dans l'onglet **Comptes** (dans la ligne de boutons décrite en §6.1), l'active ou le désactive pour les deux onglets à la fois. Inactif par défaut = 0 décimale.

**Exceptions** : l'onglet Budget affiche toujours 0 décimale, indépendamment de ce réglage (§6.3). L'onglet Évolution affiche également toujours 0 décimale, mais via son propre formateur local (`fmtVal` dans le module Évolution) — totalement indépendant de `Store.settings.decimals`, pour ne jamais être affecté si ce réglage change ailleurs (§6.4).

**À ne pas confondre avec** la pilule "0€" juste à côté (§6.1) : celle-ci ne masque que l'affichage des comptes à solde nul dans l'onglet Comptes (`Store.settings.hideZeroAccounts`) — un réglage local à cet onglet, sans lien avec le nombre de décimales ni avec aucun autre onglet.

## 6. Onglets
Cinq onglets dans la barre de navigation principale, dans cet ordre : **Comptes** (premier, onglet par défaut au démarrage), **Transactions**, **Budget**, **Évolution**, **Récurrent** — plus deux onglets secondaires derrière un bouton "⋯" en fin de barre plutôt que d'ajouter des icônes permanentes (§11, §12) : **Revenus** (§6.7) puis **Santé** (§6.6), dans cet ordre dans `MORE_TABS`.

### 6.1 Comptes
Solde total (tous comptes), puis les comptes regroupés par type (Courant / Épargne / types libres), chaque groupe affichant son solde. Chaque compte n'affiche que son nom et son solde.

Une seule ligne de boutons sous la carte de solde, toujours sur une seule ligne même à 4 boutons sur petit écran (`display:flex;gap:8px;flex-wrap:nowrap`, les 2 boutons texte en `flex:1;min-width:0` avec `white-space:nowrap;text-overflow:ellipsis`, les 2 pilules en largeur fixe) :
- **Copier pour Excel** (`buildAccountsClipboardText` + `copyTextToClipboard`) : copie dans le presse-papiers un texte tabulé (TSV) `Compte / Solde` — une ligne par compte (2 décimales, virgule, sans séparateur de milliers pour être reconnu comme nombre par Excel FR quelle que soit sa locale), plus une ligne "Total". Collé dans Excel, ça forme directement deux colonnes. Repli automatique sur `document.execCommand("copy")` si l'API Clipboard moderne échoue ou est indisponible (ex. ouverture en `file://`). **Toujours calculée sur l'ensemble des comptes**, indépendamment du filtre "masquer les comptes à 0 €" ci-dessous (c'est un export de données, pas une vue filtrée).
- **Réorganiser** (visible dès qu'il y a plus d'un groupe de type) : pop-up avec flèches haut/bas par groupe (`openAccountTypeReorderSheet`). L'ordre choisi est mémorisé dans `Store.settings.accountTypeOrder` et persiste entre les sessions — inclus dans la sauvegarde `.json`/Gist, mais plus dans l'Excel depuis le retrait de `Reglages_Generaux` (§7.2). Porte toujours sur la liste complète des types, même quand un type est momentanément masqué par le filtre "0 €" ci-dessous.
- Bouton décimales (§5).
- **Masquer les comptes à 0 €** (pilule "0€", `U.hideZeroAccountsBtnHtml`/`U.toggleHideZeroAccounts`) : filtre l'affichage des comptes dont le solde arrondit à 0,00 € au centime près (`U.isZeroBalance(bal)` = `Math.round(bal*100)/100===0`, pour couvrir aussi bien un solde exactement nul qu'un résidu de calcul flottant qui s'arrondirait à zéro). Réglage propre à cet onglet (`Store.settings.hideZeroAccounts`, **local à l'appareil**, jamais synchronisé — §7.2) : ne touche ni au solde total, ni aux soldes personnalisés, ni à la copie Excel, ni à aucun autre onglet. Un groupe de type de compte qui n'a plus aucun compte visible une fois le filtre appliqué n'est simplement pas affiché (son en-tête disparaît aussi).

Taper sur un compte filtre les Transactions sur ce compte.

**Soldes personnalisés** (`Store.settings.customBalances`, tableau de `{title, accounts}`) : jusqu'à 2 soldes additionnels, chacun calculé sur une sélection de comptes choisie par l'utilisateur, affichés dans le bloc solde à côté du solde total. Un titre vide masque le solde correspondant. Inclus dans la sauvegarde `.json`/Gist, mais plus dans l'Excel depuis le retrait de `Comptes_Soldes_Perso` (§7.2).

- **Chargement automatique au scroll** : plus de bouton "Charger plus"/"Afficher plus de groupes" — un `IntersectionObserver` sur une sentinelle en bas de liste (`#txn-scroll-sentinel`, `setupTxnInfiniteScroll`) incrémente `APP.state.txnGroupsShown` (+20) quand elle approche du viewport (`rootMargin:"600px"`, chargement anticipé). Le "Afficher plus (N restantes)" **au sein** d'un groupe déjà ouvert (au-delà de 10 transactions) reste, lui, un bouton manuel (`txnPerGroupShown`).

**Carte d'une transaction — 3 lignes, compactes, bloc élargi** (`makeTxnItemEl`) :

- **Ligne 1** (`.txn-title`, gras) : remarque, ou "Transfert X → Y", ou catégorie/"Revenu"/"Dépense" par défaut (`txnTitle`, inchangée). **Passe à la ligne si nécessaire** (`white-space:normal;overflow-wrap:break-word`, plus de troncature avec points de suspension) — une remarque longue s'affiche donc en entier, sur autant de lignes que nécessaire, quitte à agrandir la carte.

- **Ligne 3** (`.txn-line`, la plus discrète) : Date courte · Groupe — `txnLine3`.

**Fiche transaction (détail + édition unifiées)** — `openTxnDetail(id, navIds?)` (existante, `navIds` optionnel — voir "Navigation précédent/suivant" ci-dessous) et `openTxnNew()` (création, bouton "Plus" du bouton flottant) convergent toutes deux vers `renderTxnDetail(id, seed, navList)` ; `openTxnEdit(id)` reste un alias conservé pour compatibilité avec d'éventuels appelants externes, sans navigation (l'ancien alias `openTxnForm` a été retiré, jamais appelé). **Chaque champ se modifie au tap direct, sans mode "Modifier" séparé** : toucher la ligne Groupe ouvre le picker Groupe, toucher Montant ouvre un éditeur compact, etc. Plus aucune icône ronde de type en haut de la fiche.

- **Remarque en titre** : au-dessus du bloc "Détails", en gras 19px (plus grand que le reste), "(Sans titre)" en grisé si vide — reste tactile comme les autres champs (ouvre `openInlineEditor` en mode multiligne, ci-dessous).
- **Bloc "Détails"** (une seule carte) : chaque champ y est une ligne tactile (`.txn-tap-row`, retour visuel `:active`, chevron `›` en fin de ligne) — **Montant** (en premier, police 21px/900 nettement plus grande que les autres lignes pour rester facile à repérer et modifier, coloré selon le signe), **Date**, **Type**, **Compte** (ou **Compte source**/**Compte cible** si virement, champs Catégorie/Personne masqués dans ce cas), **Catégorie**, **Personne**, **Groupe**.
- **Pickers réutilisés tels quels** pour Catégorie (`categoriePickerHierarchy()`, groupée par type Revenus/Dépenses — en-têtes non sélectionnables et sections dépliées par défaut puisqu'une catégorie a toujours un type, cf. `selectableHeaders:false`/`expandedByDefault:true` sur la hiérarchie retournée), Personne (`AGG.personneHierarchy`, groupée par groupe de personnes), Groupe (`AGG.groupeHierarchyChrono`, tri chronologique, §2.1 bis), Compte/Compte cible (liste plate) ; Type via un picker à 3 options fixes avec `noEmpty:true` (pas d'entrée "Aucun(e)", champ toujours requis).
- **`openInlineEditor(opts)`** (nouvelle fonction, réutilise `overlay-confirm`/`modal-confirm` — une modale compacte, pas la sheet plein cadre des pickers) : édite Montant (`inputType:"number"`), Date (`inputType:"date"`) ou Remarque (`multiline:true`, `<textarea>`) via un simple champ + Annuler/Enregistrer.
- **Transaction existante — chaque champ s'enregistre immédiatement** (`commit(patch)`) : reconstruit la ligne complète (`DATA.rowToTxn` a besoin de tous les champs à la fois) et remplace l'entrée dans `Store.transactions`. L'id étant dérivé du contenu (`buildTxnId`), il **change à chaque modification** — suivi via une variable `currentId` fermée sur la fiche ouverte (`APP.state.detailTxnId` mis à jour en parallèle) tant qu'elle reste affichée ; passer le Type à/depuis "Transfert" vide au passage Catégorie/Personne ou Compte cible selon le sens du changement. Sauvegarde asynchrone (`Store.saveTransactions`) + rafraîchissement de l'onglet courant après chaque champ, comme avant pour un enregistrement de formulaire complet.
- **Nouvelle transaction (y compris "Dupliquer" ci-dessous)** : les champs sont d'abord accumulés dans un brouillon local (`draft`, montant non défini au départ pour forcer une saisie active — "Toucher pour ajouter") puis validés en un seul geste via le bouton **Enregistrer** (mêmes contrôles qu'avant : date et montant > 0 requis, sinon toast d'erreur ; anti-collision d'id par suffixe aléatoire si besoin).
- **Boutons du bas** : transaction existante → flèche précédente (`#td-nav-prev`, si contexte de navigation — voir plus bas) + **Dupliquer** (`#td-duplicate`, icône seule `ICONS.copy`, plus de texte) + **Supprimer** (`#td-delete`, icône seule `ICONS.trash`) + flèche suivante (`#td-nav-next`) ; nouvelle transaction → **Annuler** + **Enregistrer** (inchangés, avec texte).
- **Dupliquer** (`td-duplicate`) : ouvre le flux "nouvelle transaction" (`renderTxnDetail(null, source)`, sans `navList`) pré-rempli avec **tous** les champs de la transaction source, date d'origine incluse (pas la date du jour) — à ajuster avant de confirmer, rien n'est enregistré tant que "Enregistrer" n'a pas été tapé.

**Navigation précédent/suivant dans la fiche transaction** — disponible uniquement quand la fiche est ouverte depuis la liste principale des transactions : `makeTxnItemEl(t, navIds)` reçoit `navIds`, calculé une seule fois par rendu (`renderTransactions` → `flattenTxnGroupIds(arr)`) en aplatissant **tous** les groupes et éléments filtrés-et-triés dans leur ordre d'affichage exact (`computeTxnGroups`), y compris les groupes repliés et au-delà de la pagination/du scroll infini affichés à l'écran — la séquence de navigation couvre donc l'intégralité du résultat filtré, pas seulement ce qui est visible à l'instant T. Les fiches ouvertes depuis un autre onglet (Budget, Récurrent, Évolution, Santé) via `openTxnDetail(id)` sans second argument n'ont pas de navigation : les flèches sont alors absentes de la fiche (pas seulement grisées).
- **Instantané figé à l'ouverture** (`nav`, copie locale de `navList` dans `renderTxnDetail`, jamais recalculée depuis les filtres tant que la fiche reste affichée) : modifier un champ qui ferait sortir la transaction du filtre actif (ex. changer de groupe alors qu'on est filtré sur ce groupe) ne casse pas la navigation ni ne fait disparaître la transaction en cours d'édition de la séquence — enchaîner plusieurs modifications reste possible sans interruption. L'id étant dérivé du contenu, `nav[navIndex]` est mis à jour avec le nouvel id après chaque `commit()` pour que la position de navigation suive la transaction éditée. **Cet instantané ne survit pas à la fermeture de la fiche** : rouvrir une transaction ensuite repart d'un `navIds` recalculé sur le filtre à jour, où une transaction sortie du filtre entre-temps n'apparaît plus — comportement voulu, le gel ne protège que le temps de l'édition en cours.
- **Trois déclencheurs équivalents** : boutons flèche (`#td-nav-prev`/`#td-nav-next`, grisés/désactivés en début/fin de séquence via l'attribut `disabled`), balayage tactile gauche/droite sur la fiche (`modal-detail.ontouchstart`/`.ontouchend`, seuil 60px avec un déplacement horizontal au moins 1,5× supérieur au vertical pour ne pas interférer avec un défilement vertical de la fiche — glisser à gauche = suivant, glisser à droite = précédent, comme une pile de photos), et flèches clavier `ArrowLeft`/`ArrowRight` (écouteur global unique posé dans `buildShell`, actif seulement quand `APP.state.txnNavActive` est renseigné, qu'aucun champ `input`/`textarea` n'a le focus, et qu'aucune autre fenêtre — sélecteur `overlay-picker`, confirmation `overlay-confirm` — n'est ouverte par-dessus la fiche).
- **Nettoyage automatique** : `closeOverlay("overlay-detail")` réinitialise systématiquement `txnNavActive` à `null` et efface les gestionnaires tactiles du modal (`modalEl.ontouchstart = modalEl.ontouchend = null`). Nécessaire car `modal-detail` est un conteneur **partagé** par de nombreuses autres fiches sans rapport (réordonner les comptes, soldes personnalisés, écrans de configuration du Budget…) — sans ce nettoyage, un ancien geste de balayage ou une navigation clavier resterait actif par erreur sur la fiche suivante affichée dans ce même conteneur.

**Confirmation avant suppression** (`APP.confirmAction(opts)`, modale générique réutilisable — `{title, text, confirmLabel, onConfirm}`, `text` supporte les sauts de ligne `\n`) : protège la suppression d'une transaction (fiche détail), d'un ajustement budgétaire (§6.3), et d'une règle groupe/personne devenue obsolète (§2.4). L'overlay `overlay-confirm` doit rester **le dernier élément du shell HTML** (après tous les autres `overlay-*`) pour toujours s'afficher au-dessus, y compris par-dessus les écrans "Gérer les groupes/personnes/types de compte/catégories" — l'ordre DOM détermine l'empilement visuel à z-index égal.

### 6.3 Budget

**Deux modes seulement** (l'ancien mode "Brut" a été retiré) :
- **"Amort. + ajouts"** (`cfg.mode==="amorti"`) : amortissement + ajustements actifs.
- **"Ajouts"** (`cfg.mode==="brut_ajout"`) : ajustements actifs, pas de lissage des catégories (pas d'amortissement).

Bouton séparé, à droite des deux boutons de mode (icône colonnes, `bg-detail-toggle-btn`) : bascule la **vue détail** (`cfg.detailView`, persisté). Activée, chaque montant (catégories, voyages, totaux de section, total de carte, "Total tous groupes") s'affiche en **3 colonnes** au lieu d'une valeur unique :
- Mode "Amort. + ajouts" : **Réel + ajout · Amorti · Total**.
- Mode "Ajouts" : **Brut · Ajout · Total**.

Chaque valeur des 3 colonnes est individuellement cliquable (classe `.bg-detail-cell`, wiring central dans `renderBudget`) et ouvre la feuille de détail correspondante, préfiltrée sur le type exact de la colonne (`filterKind`: `"reel"`, `"amorti"`, `"ajout"`, ou `"reel_ajout"` — filtre composé pour la colonne "Réel + ajout" qui regroupe deux natures à la fois, géré par `bgKindIncluded()`). Fonctionne aussi pour les voyages et pour la carte "Total tous groupes" (breakdown agrégé sur tous les groupes, catégories `Income`/`Expense` séparées + voyages). Voir §6.3.4 pour le détail du calcul Réel/Amorti/Ajout côté salaire.

**Scope** : Perso (×1) ou Couple (×2, appliqué aux transactions réelles seulement — ajustements en montant brut non multiplié).

**Vue** : Total ou **Moyenne** (renommé depuis "Moyenne/mois" pour une ligne plus courte). Divise les totaux affichés par le nombre de mois de la période affichée **compris dans la borne chronologique de l'amortissement** (`Store.settings.budget.startMonth` → `endMonth`, `amortBoundedMonths`) si l'une des deux bornes est renseignée, sinon par le nombre de mois de la période affichée complète — quel que soit le mode.

**Période affichée** (`periodPickerHtml`, en-têtes `periodFrom`/`periodTo`) : chaque borne peut être laissée **"Non définie"** — bouton "✕" à côté d'un mois renseigné pour la vider, bouton texte "Non définie" à sa place pour lui redonner un sélecteur (pré-rempli avec l'autre borne ou le mois en cours). Début non défini = toute l'historique disponible jusqu'à la fin ; fin non définie = tout ce qui suit le début, jusqu'au mois en cours ou à la dernière donnée connue si plus tardive. La borne manquante est résolue par `budgetDataMonthBounds()` (étendue mini/maxi parmi les transactions, les salaires saisis et les ajustements, mois en cours inclus comme plancher haut) avant d'être développée en liste de mois par `monthsInRange`. Élargir ainsi la période affichée **ne contourne aucune règle d'amortissement** : la fenêtre d'amortissement (§ ci-dessous), le bornage des groupes additionnels (`extraGroupEffectiveMonths`) et celui des salaires (§6.3.4) restent calculés à partir de `startMonth`/`endMonth`, indépendamment de la taille de la période affichée. Bloc affiché sur deux lignes (libellé au-dessus, dates en pleine largeur en dessous, sans forme pilule) plutôt qu'en une seule ligne compressée, pour que les mois longs (ex. "septembre 2026") restent lisibles à côté du bouton "✕". Persisté comme avant (`Store.settings.budget.periodFrom`/`periodTo`, peut désormais valoir `null`).

L'onglet Budget affiche toujours les montants **sans décimale**, indépendamment du réglage global de décimales (§5).

**Quatre boutons toujours visibles, sur une seule ligne**, ouvrent chacun un pop-up dédié :
- **Amortissement** → mois de début, période de lissage (calculée automatiquement), catégories amorties (pilules One UI), case **"Ne pas distinguer les voyages"** (regroupement global, §6.3.2 bis) ; sous-libellé "Inactif (mode Ajouts)" quand `cfg.mode !== "amorti"`.
- **Ajustements** → liste des ajustements de la période ; sous-libellé "N sur la période" ou "Aucun" (formulaire détaillé en §6.3.6).
- **Comparaison** → réglages de comparaison ; sous-libellé la période comparée, "Budget prédéfini", ou "Désactivée".
- **Comptes exclus** → pilules One UI cliquables, une par compte ; sous-libellé "N exclu(s)" ou "Aucun".

#### 6.3.1 En-tête de colonnes figé ("Total tous groupes")
Quand une comparaison est active OU que la vue détail est activée, un en-tête de colonnes (`compareHeaderRowHtml()` ou `detailHeaderRowHtml(cfg.mode)`) est affiché **au-dessus** de la carte "Total tous groupes", dans sa propre petite carte flottante, en `position:sticky;top:0;z-index:10`, directement enfant de la section qui contient aussi toutes les cartes de groupes en dessous. Sa "boîte englobante" pour le calcul du sticky est donc **toute la section**, pas seulement la petite carte de total — il reste figé en haut de l'écran pendant tout le défilement de la liste des cartes de groupes, jusqu'à la fin de la section (et non plus seulement le temps de défiler la petite carte de total elle-même, erreur d'une implémentation précédente).

#### 6.3.2 En-tête de carte de groupe
Nom du groupe + chevron cliquable → ouvre un sélecteur pour **changer** le groupe occupant cette carte. Icône avion ✈️ (voir §6.3.2 bis) pour regrouper les voyages de cette carte précise dans ses catégories. Pour un groupe additionnel uniquement, un bouton **Retirer** (✕) supplémentaire. Les groupes additionnels suivent toujours les mêmes mois que le principal (`extraGroupEffectiveMonths` = intersection période affichée / borne d'amortissement, comme le diviseur de la vue Moyenne).

**Carte du groupe principal et d'un groupe additionnel** : structure identique — Total + listes **Revenus**, **Dépenses** et **Voyages**, chaque ligne cliquable → ouvre le détail des transactions correspondantes (ou les 3 colonnes cliquables si vue détail active, §6.3). Les sections Revenus/Dépenses/Voyages sont repliables (`<details>`) mais partagent un **seul état global** (`allSectionsOpen`).

#### 6.3.2 bis Regrouper les voyages dans les catégories ("Ne pas distinguer les voyages")
Par défaut, un groupe de type Voyage (`getGroupKind`, §2.1) est affiché à part : ses transactions alimentent le bloc "Voyages" de sa carte (une ligne par occurrence de voyage), jamais les listes Revenus/Dépenses par catégorie. Deux réglages, cumulables (`voyagesMergedForGroup(groupName)` = l'un OU l'autre), permettent de désactiver cette distinction et de fondre ses coûts/revenus dans les catégories du groupe, comme une transaction "vie quotidienne" ordinaire :
- **Réglage global** (`Store.settings.budget.mergeVoyages`, case dans la fiche Amortissement, §6.3) : s'applique à **tous** les groupes de la carte (principal et additionnels) sans distinction.
- **Réglage par groupe** (`Store.settings.budget.mergeVoyagesGroups`, tableau de noms de groupe) : icône avion dans l'en-tête de chaque carte (§6.3.2), cliquable, colorée (fond primaire) quand active pour cette carte précise, grisée sinon. Indépendant d'une carte à l'autre — activer le regroupement sur le groupe principal n'affecte jamais un groupe additionnel, et inversement.

**Le regroupement ne change jamais le mois de comptage d'une transaction, ni son éligibilité à l'amortissement — seule la ligne sous laquelle elle apparaît change.** La résolution du mois d'une transaction de groupe Voyage (`voyageTxnMonths()`, fonction centralisée partagée par `computeGroupBudget`, `openCategoryTxnSheet` et `collectGroupTypeItemsDetailed`, pour que le total affiché et le détail cliquable restent toujours cohérents entre eux) garde la même priorité, fusionné ou non : "Mois voyage" forcé (§2.4) d'abord, sinon date corrigée (transform, §1.3 — un seul mois, ou réparti 1/12 par mois sur l'année en `yearsplit`), sinon date réelle. Une transaction de groupe Voyage n'est jamais amortie, fusionnée ou non — le regroupement change uniquement la case de destination (catégorie du groupe au lieu du bucket Voyages), jamais le calcul du montant ni son mois.

*Bug corrigé en cours de développement* : une première version forçait le traitement "vie quotidienne" en bloc pour un groupe fusionné, ce qui faisait perdre la priorité du "Mois voyage" forcé au profit de la seule date corrigée/réelle — une dépense ou un revenu pouvait alors se retrouver compté sur un mois différent selon que le regroupement était actif ou non, changeant le total affiché sur une période donnée au lieu de simplement changer sa ligne d'affichage. Corrigé en centralisant la résolution du mois dans `voyageTxnMonths()`, utilisée identiquement que le regroupement soit actif ou non.

#### 6.3.3 Détail d'une catégorie (tap sur une ligne "Catégories")
- Cas spécial **catégorie "Salaire"** (nom insensible casse/accents) : tap ouvre l'**éditeur de saisie manuelle** (§6.3.4) au lieu du détail habituel.
- Badges **Réel / Amorti / Ajout** en haut (totaux) — cliquables, servent de filtre sur la liste en dessous.
- Montant affiché par ligne = montant **utilisé par le budget**, cohérent avec les totaux de la carte.
- Chaque transaction "Réelle" a un bouton **"Amortir"** : ouvre le formulaire d'ajustement pré-rempli pour convertir cette transaction précise en dépense amortie.
- Montants "lissés sur l'année" (yearsplit) affichés au prorata de la période ; libellé court "XX/12 mois".

#### 6.3.4 Éditeur "Salaire" — décomposition Brut/Ajout
Remplace le détail habituel pour la catégorie dont le nom normalisé est "salaire". Une ligne par mois de la période, 3 colonnes : **Moi** (saisie), **Ma femme** (saisie), **Total** (calculé). Stocké dans `Store.settings.budget.salaryEntries[mois] = {moi, femme}`.

**Logique Brut/Ajout** (`salaryMonthBreakdown`, remplace l'ancien comportement où la saisie "Moi" était purement et simplement ignorée en mode "Brut" — ce mode n'existe plus) :
- Le salaire de **"Ma femme"** est **toujours entièrement "Brut"** — sa valeur déclarée n'est jamais comparée à des transactions (elle n'est en général pas suivie dedans).
- **"Moi"** : le montant des **transactions réelles** de la catégorie ce mois-là est toujours le "Brut". Si une saisie manuelle est renseignée pour le mois, elle représente le **salaire déclaré** ; l'écart entre cette valeur déclarée et le montant des transactions devient l'**"Ajout"** (positif ou négatif). Sans saisie manuelle, "Moi" = Brut seul (Ajout = 0).
- La saisie "Moi" **n'est jamais grisée** — l'ancien blocage lié au mode "Brut" a disparu avec ce mode.
- **Total** : Couple = (Brut+Ajout de Moi) + Ma femme (saisi ou 0) ; Perso = Moi uniquement.
- **Jamais compté hors de la borne chronologique de l'amortissement** (`amortBoundedMonths`, mêmes bornes `startMonth`/`endMonth` que les catégories amorties et les groupes additionnels) : un mois de la période affichée qui tombe hors de cette fenêtre ne contribue ni au Brut ni à l'Ajout du salaire, même s'il a une saisie manuelle ou des transactions réelles — cohérent avec le fait qu'une période affichée élargie (notamment via une borne "Non définie" ci-dessus) ne doit jamais faire apparaître de salaire hors de la fenêtre configurée.

Cette décomposition alimente directement `o.realIncome`/`o.adjIncome` de la catégorie Salaire dans `computeGroupBudget` (au lieu d'un total unique écrasant tout), ce qui la rend compatible avec la vue détail (§6.3) : la ligne Salaire affiche elle aussi Réel+Ajout/Amorti/Total (Amorti toujours à 0, le salaire n'étant jamais amorti).

#### 6.3.5 Comparaison
`Store.settings.budget.compare = {enabled, mode:"period"|"predefined", periodFrom, periodTo, predefined:{}}`. Une fois activée, l'affichage bascule en tableau à 3 colonnes (Résultat · Comparé · Variation). Les totaux ne sont jamais des valeurs indépendantes : toujours la somme des lignes affichées en dessous. Voyages jamais détaillés voyage par voyage en vue comparaison — une seule ligne "Total voyages", toujours affichée même à 0 €/0 €.
- **Mode "Autre période"** : le scénario comparé applique exactement les mêmes réglages que le principal, seule la période change.
- **Mode "Budget prédéfini"** : montants mensuels saisis à la main, un par catégorie de chaque groupe et un par groupe pour l'ensemble de ses voyages.

**Catégories alimentées seulement côté comparé** (`compareOnlyCategories()`) : une catégorie sans transaction dans le scénario principal sur la période affichée, mais alimentée côté comparé (transactions de l'autre période en mode "Autre période", ou clé présente dans `compare.predefined` en mode "Budget prédéfini"), n'est **jamais masquée** — elle s'affiche avec un montant principal à 0 €, plutôt que de disparaître. Sans cela, sa valeur comparée serait à la fois invisible et absente des totaux Revenus/Dépenses/Total (main + grand total) qui n'auraient sinon jamais inclus cette catégorie. Type (Revenus/Dépenses) déterminé par le classement global de la catégorie (`classifyCategoryTypes`, mêmes règles/overrides que partout ailleurs dans l'app), jamais par le signe de la valeur comparée — une ligne à 0 €/0 € côté principal n'a pas de signe propre.

**Budget prédéfini — vue Amorti/Réel/Les deux** (`Store.settings.budget.compare.predefinedVue`, objet clé→vue, même clé que `compare.predefined` — `predefinedCatKey`/`predefinedVoyageKey`) : chaque montant prédéfini (une catégorie, ou "Voyages" d'un groupe) peut être associé à l'une des deux vues du Budget (§6.3) plutôt qu'affiché identique dans les deux, quand le montant saisi représente délibérément un scénario "avec amortissement" ou "réel" et non une moyenne valable dans les deux cas. Réglable via 3 boutons sous chaque montant, dans la fiche "Budget prédéfini" (`openPredefinedBudgetSheet`, n'apparaissent que si un montant est saisi pour cette ligne) :
- **Les deux** (`"both"`, absence de clé — comportement historique, par défaut pour toute ligne existante) : montant affiché identique quel que soit le mode affiché, jamais ajusté.
- **Amorti** (`"amorti"`) : montant affiché tel quel en vue "Amort. + ajouts" ; en vue "Ajouts", la part d'amortissement de cette ligne en est **retirée** (montant − amortissement).
- **Réel** (`"reel"`) : montant affiché tel quel en vue "Ajouts" ; en vue "Amort. + ajouts", cette même part d'amortissement y est au contraire **rajoutée** (montant + amortissement).

La "part d'amortissement" d'une ligne n'est pas un chiffre saisi à part : c'est la contribution `amortIncome`/`amortExpense` réellement calculée pour cette même catégorie (ou pour la ligne "Ajustements" côté voyages, seule à pouvoir en porter une) par `computeGroupBudget`, **recalculée en forçant le mode "amorti"** même quand la vue actuellement affichée est "Ajouts" (nouveau paramètre `opts.mode` de `computeGroupBudget`, résultat mis en cache par groupe dans `computeCompareContext.getAmortResult`, jamais appliqué à un groupe additionnel qui reste toujours en brut comme partout ailleurs dans le Budget). Mise à l'échelle Total/Moyenne identique au montant prédéfini lui-même (÷ nombre de mois effectifs du groupe en vue Moyenne, valeur brute en vue Total).

*Exemple* : un montant prédéfini de 1000 € de dépense scopé "Réel", avec par ailleurs 700 € d'amortissement calculés sur cette même ligne, affiche **1000 €** en vue "Ajouts" et **1700 €** en vue "Amort. + ajouts" (700 € rajoutés). Le même montant scopé "Amorti" afficherait **1000 €** en "Amort. + ajouts" et **300 €** en "Ajouts" (700 € retirés). Scopé "Les deux", il afficherait 1000 € dans les deux vues. Persisté en Excel (colonne "Vue (Amorti/Réel/Les deux)" de `Budget_Predefini`, §7/§8) et en JSON/Gist (`comparePredefinedVue`, §7.2) — fusionné clé par clé comme `compare.predefined` en mode "Ajouter" (jamais écrasé si déjà renseigné localement).

**Clic sur la cellule "Comparé"** : chaque valeur de la colonne "Comparé" (catégorie, Total voyages, Total de carte, Total Revenus/Dépenses, grand total tous groupes) est individuellement cliquable (classe `.bg-cmp-cell`, wiring central dans `renderBudget`) et ouvre **exactement la même feuille de détail** que le scénario principal (mêmes badges Réel/Amorti/Ajouts filtrables, même liste, même logique d'amortissement) — mais avec les montants de la **période comparée** au lieu de la période affichée, via `opts.periodOverride` transmis à `openCategoryTxnSheet`/`openVoyageTxnSheet`/`openGroupTypeTxnSheet`. En mode "Budget prédéfini" (pas de transactions sous-jacentes à lister), le clic ouvre à la place l'éditeur du budget prédéfini, seule source réelle de ce montant. Les cellules "Résultat" et "Variation" ne sont jamais individuellement cliquables : un clic dessus continue de remonter au gestionnaire de la ligne entière (scénario principal, comportement inchangé).

#### 6.3.6 Ajustements manuels — formulaire (`openAdjustmentForm`)
Champs : mois, **groupe** (voir ci-dessous), catégorie (vide = ajustement global au groupe, imputé en `Ajustements` parmi les voyages, §6.3.2), montant (négatif = dépense), remarque, scope de saisie (Perso ×1 / Couple ×2 / Les deux, §6.3), case "n'apparaît que dans cette vue" (`montantViewOnly`), case "Amortir ce montant sur toute la période" (`amorti`).

**Champ Groupe** : bouton (`PICKER.fieldPickerBtnHtml`) ouvrant le même picker hiérarchique que la fiche transaction (§6.2), via `adjustmentGroupHierarchy()` — reprend tel quel `AGG.groupeHierarchyChrono` (§2.1 bis) : groupes de groupe sélectionnables en bloc (en-tête de section), triés du plus récent au plus ancien, chaque groupe précis sélectionnable individuellement en dessous (trié du plus ancien au plus récent), groupes non classés à part (triés alpha). Avant cette évolution, seuls les groupes de groupe étaient proposés (`candidateSuperGroupes()`, retirée) — un ajustement peut désormais cibler **n'importe quel groupe**, précis ou de groupe, exactement comme un groupe principal/additionnel du Budget (§6.3.2) peut lui-même être l'un ou l'autre.

Chaque groupe précis (jamais les en-têtes, un groupe de groupe pouvant mélanger les deux types) est précédé d'une icône Voyage ✈️/Vie quotidienne 🏠 (`getGroupKind`, §2.1) via le paramètre `h.kindFn` de `renderPickerList` (§12) — pour voir en un coup d'œil, au moment de choisir, dans quelle case budgétaire (catégories "vie quotidienne" vs bloc "Voyages", §6.3.2) l'ajustement ira une fois enregistré.

**Correspondance stricte, pas de repli hiérarchique** : `adj.groupe` est comparé par **égalité stricte** au nom du groupe actuellement configuré pour la carte (`cfg.mainGroup`/un élément de `cfg.extraGroups`) — jamais via `groupSelectionMatches` (utilisée pour les transactions, qui accepte aussi le nom de base en repli). Un ajustement ciblant le groupe de groupe "Voyages Europe" ne s'applique donc **pas** automatiquement si la carte est configurée sur le groupe précis "Voyage Italie (24-05)", et inversement — le champ Groupe de l'ajustement doit correspondre **exactement** à ce qui est choisi pour la carte (§13).

### 6.4 Évolution
Vue tabulaire de l'évolution d'une dimension dans le temps, avec drill-down année → mois, affichage cumulé ou par période (§6.4.2 bis) et ouverture directe de la liste de transactions depuis n'importe quel montant.

#### 6.4.1 Dimensions et sections
Sélecteur de vue à 4 boutons (`Store.settings.evolution.view`, persisté) : **Groupe**, **Catégorie**, **Personne**, **Compte**.
- **Groupe** : sections = groupe de groupe résolu (§2.1), items = libellé complet du groupe.
- **Catégorie** : sections = Revenus/Dépenses (classification via `classifyCategoryTypes`, avec override), items = catégorie.
- **Personne** : sections = groupe de personnes résolu, items = personne.
- **Compte** : sections = type de compte (§3), items = compte. Seule dimension où les **virements sont inclus** (les 3 autres les excluent, comme partout ailleurs dans l'app) : un virement contribue `-montant` au compte source et `+montant` au compte cible, exactement comme `computeAccountBalances` — un même virement peut donc alimenter deux items à la fois. Le total général ("Total" en haut, §6.4.4) neutralise toujours les virements internes (ils s'annulent par construction en sommant toutes les sections).

Moteur d'agrégation : `AGG.buildEvolutionIndex(dimension, monthBasis)`, retourne `{sections:[{key,label,items:[{key,label,values:Map("YYYY-MM"→montant)}]}]}`. Les sections/items sont triés par montant total décroissant.

#### 6.4.2 Base mensuelle : réel vs transformé
Sélecteur à 2 boutons (`Store.settings.evolution.monthBasis`, persisté) :
- **Mois réel** : chaque transaction est comptée sur sa date réelle (`t.date`), sans tenir compte d'une éventuelle Remarque de transformation.
- **Mois transformé** : applique `t.transform` (§1.3) — une transaction "yearsplit" est répartie également sur les 12 mois de son année cible, exactement comme dans le moteur Budget.

#### 6.4.2 bis Mode cumulé
Troisième sélecteur à 2 boutons ("Normal"/"Cumulé", `Store.settings.evolution.cumulative`, persisté **localement** — volontairement absent de `buildParamsPayload`, §7.2, comme `theme` : un réglage d'affichage courant, pas une donnée de configuration à synchroniser entre appareils).

En mode Cumulé, chaque colonne (année ou mois) affiche la somme de toutes les valeurs depuis le tout début des données jusqu'à cette période incluse — comparaison lexicographique directe sur les clés `"YYYY-MM"` de `item.values` (valide car le mois y est toujours sur 2 chiffres, pas de tri numérique nécessaire) : `AGG.itemCumulativeYearValue`/`sectionCumulativeYearValue` (borne = décembre de l'année), `AGG.itemCumulativeMonthValue`/`sectionCumulativeMonthValue` (borne = le mois exact). La cumulation reste continue au travers d'un drill-down : le mois de décembre d'une année affichée cumule tout l'historique jusqu'à cette année incluse, pas seulement les mois de l'année en cours de consultation.

**La colonne "Total" n'est jamais recalculée par ce mode** — elle reste toujours la somme brute (`itemTotalValue`/`sectionTotalValue`, comme en mode Normal), ce qui garantit que le total affiché est strictement identique dans les deux modes.

Le clic sur un montant en mode Cumulé ouvre la même feuille de détail qu'en mode Normal (§6.4.3), mais avec les transactions cumulées correspondantes — toute transaction dont la période est antérieure ou égale à la colonne cliquée (`txnMatchesPeriod(t, monthBasis, year, month, cumulative:true)`) — et un intitulé de période adapté ("Jusqu'à *période* (cumulé)" au lieu de la période seule). Un clic sur la colonne "Total" reste inchangé dans les deux modes ("Toute la période"), cohérent avec le fait que cette colonne ne cumule jamais.

#### 6.4.3 Colonnes et drill-down
Tableau HTML (`<table class="evo-table">`, pas de grille CSS) pour un comportement de colonnes figées fiable : les 2 premières colonnes (**Libellé**, **Total**) sont en `position:sticky;left:...`, avec des largeurs fixes en pixels et `box-sizing:border-box` sur toutes les cellules (indispensable — sans ça, le padding s'ajoute aux `min/max-width` et désaligne l'offset `left` de la 2ᵉ colonne figée, provoquant un chevauchement visuel avec la 1ʳᵉ). Les colonnes suivantes défilent horizontalement : une par **année** par défaut, ou une par **mois** (Jan.→Déc.) après un clic sur une année.

**Largeur et défilement** : le bloc tableau (`.section` qui l'englobe) utilise un padding latéral réduit à 8px au lieu des 20px standard, et les colonnes Total/valeur partagent une largeur compacte uniforme de 74px (au lieu de 82/78px auparavant) — Total + 2 colonnes de mois/années tiennent ainsi sans défilement dans le cas courant. Au-delà, le défilement horizontal se fait à la main : `U.enableDragScroll(el)` (module Utils, §12) attache un glisser-déposer souris (`mousedown`/`mousemove`/`mouseup` globaux, classe `.evo-table-wrap.drag-scroll-active` pendant le geste, `cursor:grab`/`grabbing`) en plus du défilement tactile natif déjà actif via `overflow-x:auto` — un léger seuil de déplacement distingue un clic (ouvre la feuille de détail) d'un glissé (fait défiler), pour ne jamais déclencher les deux à la fois. Repris tel quel par l'onglet Récurrent (§6.5) et par la vue mensuelle du Budget.

- **Clic sur une année** (en-tête de colonne, `.evo-year-header`) : `drillYear` passe à cette année, le tableau réaffiche 12 colonnes mensuelles pour cette année, avec un bouton "Retour aux années". **La colonne "Total" affiche alors le total de l'année sélectionnée** (pas le total toutes années confondues) — pour les sections, les items, et la ligne "Total" générale ; elle redevient le total toutes années dès qu'on revient à la vue par années.
- **Clic sur un montant** (n'importe quelle cellule de valeur, `.evo-val-cell`) : ouvre `openEvolutionTxnSheet(dimension, opts)`, qui filtre `Store.transactions` par correspondance de dimension (`txnMatchesDimTarget`) et de période (`txnMatchesPeriod`, mêmes règles de redistribution mensuelle qu'en §6.4.2) puis affiche la liste triée par date, avec un badge Total.
- **Clic sur le libellé d'une section** : replie/déplie ses items (état non persisté, tout replié par défaut au premier rendu de chaque nouvelle combinaison vue/dimension).

Vue **Groupe** uniquement : sections et items ne sont **pas** triés par montant (contrairement aux 3 autres dimensions, cf. §6.4.1) mais chronologiquement, cf. §2.1 bis.

#### 6.4.4 Ligne "Total" générale
Première ligne du tableau (sous l'en-tête, toujours visible, jamais repliable), somme de toutes les sections pour chaque colonne. Cliquable comme le reste (`data-global="1"`) — ouvre la liste de **toutes** les transactions de la dimension pour la période cliquée, sans filtre de section/item (`opts.global` court-circuite `txnMatchesDimTarget`).

#### 6.4.5 Fusion de sections
**Ne se crée plus depuis l'onglet Évolution** — les boutons de sélection/fusion ("Fusionner des …" / "Fusionner (N)" / modale de saisie du nom) ont été retirés de l'interface. Une fusion (`{name, members:[clés de section]}`, stockée dans `Store.settings.evolution.merges[dimension]`, une liste par dimension) se configure désormais **uniquement via la sauvegarde `.json` ou la synchronisation Gist** (§7.2) — l'ex-feuille Excel dédiée `Evolution_Fusions` a été retirée (§7.2, §8), l'Excel ne permet donc plus de créer, lire ni transférer une fusion de sections.

L'onglet Évolution se limite à :
- **Afficher** les fusions actives sous forme de chips sous les sélecteurs de vue.
- **Supprimer** une fusion individuellement (bouton × sur sa chip, défusion immédiate et persistée localement).

La mécanique de fusion elle-même est inchangée : à l'affichage, `buildEvolutionIndex` fusionne toujours les sections membres en une seule section synthétique (`__merged:true`, items préfixés en interne pour éviter les collisions de clé mais affichés sous leur libellé d'origine) — seule la **création** depuis l'interface a été retirée, pas le calcul ni l'import/export.

Inclus dans la sauvegarde `.json`/Excel/Gist, fusionné par dédoublonnage à l'import (§7.2) — contrairement à la vue actuellement affichée (`evolution.view`/`monthBasis`/`cumulative`), jamais modifiée par un import "Ajouter".

### 6.5 Récurrent
Cinquième onglet (icône `refreshCw`). Isole les transactions dont la Remarque porte un suffixe de date transformée (`AA-MM` ou `AAAA`, §1.3, `t.transform.mode !== "same"`) — celles dont le **mois calculé** diffère du mois réel — regroupées par catégorie, pour suivre des dépenses/revenus récurrents (abonnements, loyers…) indépendamment de leur date réelle d'enregistrement. Même format visuel que l'onglet Évolution (tableau à colonne Libellé figée, sections repliables, montants cliquables, défilement compact §6.4.3), avec ses propres particularités ci-dessous.

**Moteur** : `AGG.buildRecurringIndex(periodFrom, periodTo)` — sections = catégorie (`t.categorie || "(Non renseigné)"`), items = **nom de la transaction sans le suffixe de date** (`U.baseRemarque(remarque)`, symétrique de `computeTransform` : retire `AA-MM`/`AAAA` en fin de chaîne, retourne la remarque telle quelle si aucun suffixe n'est reconnu). Items triés **alphabétiquement** au sein de chaque section (pas par montant) ; sections triées par montant absolu décroissant, comme les autres dimensions d'Évolution.

**Colonnes** : Total de la période, puis une colonne par mois. Une entrée `AA-MM` alimente son mois précis (`item.values`, clé `"AAAA-MM"`) ; une entrée `AAAA` (répartition sur l'année, §1.3) **n'est pas éclatée sur 12 mois** ici, contrairement au moteur Budget/Évolution — elle reste groupée par année entière (`item.yearValues`, clé `"AAAA"`) et s'affiche dans une **colonne spéciale juste après décembre** de cette année-là (`AGG.recurringColumns`, insère la colonne année uniquement pour les années qui ont effectivement une entrée de ce type). La colonne Total **n'est pas figée** (contrairement à Évolution) : c'est simplement la première d'une séquence `[Total, ...colonnes de période]` qui défile comme les autres — seule la colonne Libellé reste sticky.

**Filtre de période** (`Store.settings.recurrent.periodFrom/periodTo`, deux `<input type="month">`) : porte uniquement sur le **mois calculé** des entrées `AA-MM`, ou sur décembre de l'année pour une entrée `AAAA` (cohérent avec son positionnement de colonne) — jamais sur le mois réel. Par défaut, la période couvre tout l'historique disponible (`ensureRecurrentPeriod`, calculée une fois puis persistée) pour ne rien masquer au premier affichage.

**Tout déplier/replier** (`#rec-expand-toggle`) : même mécanisme que Transactions (§6.2) — réglage global persistant `Store.settings.recurrent.groupsExpanded`, dépassements individuels par section effacés au clic sur le bouton global.

**Clic sur un montant** : ouvre `openRecurringTxnSheet(opts)` (feuille de détail dédiée, même esprit que `openEvolutionTxnSheet` côté Évolution) ; le filtrage (`txnMatchesRecurringTarget`) distingue trois cas — colonne d'un mois précis, colonne année spéciale, ou colonne Total (auquel cas le filtre de période s'applique, mêmes règles que l'agrégation). Chaque ligne de la feuille ouvre à son tour la fiche transaction standard (`openTxnDetail`, §6.2).

### 6.6 Santé
Onglet secondaire, indépendant des Transactions (données, filtres et listes propres) mais reprenant volontairement la même présentation — bouton flottant, style de carte, fiche détail par tap direct. Accessible via le bouton "⋯" (`#nav-more`, dernière position de la barre de navigation) qui ouvre une petite sheet (`overlay-more`/`sheet-more`, `openMoreMenu()`) listant les onglets secondaires — `MORE_TABS = [{key:"revenus",...}, {key:"sante",...}]`, Revenus en premier (§6.7) — et s'allume comme actif dès que `currentTab` fait partie de `MORE_TAB_KEYS`. `showFloat` (§6.2) inclut désormais `"sante"` en plus de `"transactions"` (pas `"revenus"`, qui n'a pas de bouton flottant, §6.7) ; les 4 boutons du bouton flottant se dispatchent selon `currentTab` vers les fonctions Santé ou Transactions correspondantes.

**Modèle** (`Store.santeItems`, un item = un soin) :
```
{ id, dateSoin, beneficiaire, devise, montantEur, montantDevise,
  medecin, typePrestation, statut, statutDate,
  rembTiersMontant, rembTiersDate, rembSecuMontant, rembSecuDate, rembMutuelleMontant, rembMutuelleDate,
  groupe, mutuelle, partMoi, termine }
```
`montantDevise` n'existe que si `devise !== "€"` (sinon toujours `null`) — purement informatif à côté de `montantEur`, aucune conversion/taux de change automatique. `id` = hash de contenu (`buildSanteId`, même principe que `buildTxnId`, §1.2) sur `dateSoin/beneficiaire/typePrestation/medecin/montantEur/groupe/statut` — **`termine` en est volontairement exclu** : basculer ce statut ne doit ni changer l'id ni casser la déduplication à l'import (ci-dessous).

**"Ma part"** (`computeMaPart(it)`) = `montantEur × partMoi ÷ 100`, arrondi à la **2ᵉ décimale inférieure** (`Math.floor`, jamais un arrondi standard) — affichée à côté du pourcentage dans la fiche (ligne "Part moi") et en totaux filtrés dans l'en-tête de liste (ci-dessous).

**Statut "Terminé"** (`termine`, booléen) : bouton pilule en haut de la fiche détail (`#sd-termine`, à gauche du bouton fermer), bascule immédiate avec sauvegarde pour un soin existant, simple mise à jour du brouillon pour un nouveau soin. Un soin terminé s'affiche légèrement grisé dans la liste (`opacity:0.6`) avec "✓ Terminé" ajouté en ligne 3 de sa carte. Filtrable (2 puces fixes Terminé/Non terminé, même présentation que le filtre Type des Transactions) et regroupable (mode d'affichage dédié, non-terminés triés avant terminés plutôt qu'alphabétiquement).

**Listes personnalisables** (`Store.settings.sante.lists`, 6 clés : `beneficiaires, devises, medecins, prestations, statuts, mutuelles` — `devises` pré-rempli `["€","$","£","CHF"]` à la première utilisation si vide) : chaque champ concerné utilise `PICKER.openPicker({..., allowNew:true})`, et toute valeur saisie à la volée est ajoutée automatiquement à la liste correspondante (`addToList`) — gérables aussi depuis Santé → bouton réglages (ajout/suppression simple, ci-dessous). **Le champ Groupe fait exception** : il ne pioche pas dans une liste Santé mais directement dans la hiérarchie des groupes des Transactions (`AGG.groupeHierarchyChrono(Store.transactions)`), présentée et filtrée comme le filtre Groupe habituel (§2.1 bis, §4) — texte libre accepté aussi (`allowNew:true`), sans obligation d'exister déjà côté Transactions.

Sélectionner un **Statut** horodate automatiquement `statutDate` à aujourd'hui ; modifiable ensuite via la ligne "Mise à jour le", séparée, saisie manuelle.

**Liste et filtres** (`window.__SF_SANTE_FILTERS`, dimensions `beneficiaires/prestations/statuts/devises/groupes` en `Set` + `termine` + `search`, persistés dans `Store.settings.santeFilters`) : sheet de filtre à **page unique** (pas le menu en deux étapes des Transactions, §4), réutilisant `overlay-filter`/`sheet-filter` — un seul des deux filtres (Transactions ou Santé) affiché à la fois selon l'onglet courant. Le filtre Groupe y affiche les mêmes comptes que le filtre Groupe des Transactions (comptages sur `Store.transactions`, pas sur les soins) — cohérent avec le choix de piocher dans la même hiérarchie, mais à garder en tête si un compte affiché semble élevé par rapport au nombre de soins réellement rattachés.

**Affichage** (`openSanteDisplayMenu`, réutilise `overlay-dispmenu`/`sheet-dispmenu`) : regroupement par Mois (défaut), Bénéficiaire, Statut, Groupe, Médecin/hôpital ou Terminé (`SANTE_GROUPBY_LABEL`) — cartes de groupe **toujours dépliées**, pas de pagination ni de scroll infini comme les Transactions (§6.2), le volume de soins étant nettement plus faible. En-tête de liste : nombre de soins + montant total filtré, puis Remboursé/Reste à charge/Ma part (`computeSanteTotals`, sommés sur les soins filtrés), puis le pill "Affichage".

**Fiche soin** (`renderSanteDetail(id, seed)`, réutilise `overlay-detail`/`modal-detail` comme la fiche transaction, §6.2 — même principe de tap direct par champ, pas de mode "Modifier" séparé) : bouton Terminé + fermer en haut, titre "Type de prestation" tactile, puis cartes **Soin** (Montant €, Devise, Montant devise si ≠ €, Date du soin, Bénéficiaire, Médecin/hôpital, Groupe), **Statut** (Statut + date de mise à jour) et **Remboursements** (Tiers payant/Sécu/Mutuelle, chacun ouvre `openReimbEditor` — mini-modale montant+date compacte, réutilise `overlay-confirm`/`modal-confirm`) et **Mutuelle & part** (Mutuelle, Part moi — `openPartMoiEditor`, pilules rapides 0/50/100 % + saisie manuelle, affiche "Ma part" calculée à côté). Nouveau soin : brouillon local, "Enregistrer" exige date + montant > 0 (mêmes contrôles que Transactions, §6.2) ; soin existant : **Dupliquer**/**Supprimer** (confirmation via `APP.confirmAction`).

**Réglages Santé** (bouton dédié en haut de l'onglet, `#sante-settings-btn`, propre à Santé — n'apparaît pas dans le Menu ☰ général) : `window.__SF_SANTE_SETTINGS`, sheet propre (`overlay-santesettings`) avec sous-écrans (`settingsView`) — menu listant les 6 listes personnalisables (ajout/suppression simple par valeur, `renderSanteListEditor`) et deux actions Excel **dédiées à l'onglet**, distinctes des écrans du flux principal (§7/§8) mais qui ne sont plus totalement étanches à lui (mapping de colonnes et détection partagés, voir ci-dessous) :
- **Export** (`exportSanteExcel`) : une feuille "Santé" dédiée, 19 colonnes (`SANTE_XLSX_HEADER`, dont "Terminé" en `Oui`/`Non`), dates au format Excel natif `dd/mm/yyyy` sur les 5 colonnes date (mêmes principes qu'en §8). Construction des lignes factorisée dans `buildSanteExportRows()`, réutilisée telle quelle par l'export Excel principal (§8) quand la case "Santé" y est cochée — un seul mapping de colonnes entretenu, jamais dupliqué entre les deux écrans.
- **Import** (`rowToSanteItem`) : `.xlsx`/`.xls`/`.csv`, en-têtes reconnus par nom normalisé (accents/casse insensibles), montants tolérants à la virgule décimale, "Terminé" reconnu depuis `Oui/Yes/True/1/x` (sinon `Non`). Fusion (dédup par id, comme Transactions, §7) ou remplacement complet au choix, si des soins existent déjà localement ; les nouvelles valeurs rencontrées sont ajoutées automatiquement aux 6 listes personnalisables (`registerNewListValuesFromItems`). Cette même fonction `rowToSanteItem` est aussi celle utilisée par le flux d'import principal (§7) pour détecter et lire une feuille "Santé" au sein d'un classeur Transactions/Paramètres — l'écran dédié ici reste toutefois le seul point d'entrée pour un classeur **ne contenant que** des soins sous un autre nom de feuille (repli sur la première feuille du classeur si aucune n'est nommée "Santé", absent du flux principal qui exige le nom exact).

**Stockage et sauvegarde** : `Store.santeItems` en IndexedDB (clé `sante_items`, repli `localStorage` `sf_sante_items_v1`, §9) ; `Store.settings.sante`/`Store.settings.santeFilters` dans le même `localStorage` que le reste des réglages. Inclus dans la sauvegarde `.json` complète (§8) et dans le payload de synchronisation Gist (§10, remplacement complet à la récupération, jamais de fusion — même logique que pour les transactions) — et, depuis l'ajout de la case à cocher dédiée (§8), optionnellement dans l'export Excel multi-feuilles principal également, si le classeur importé contient une feuille "Santé" (détection par nom exact, §7). "Réinitialiser toutes les données" (Menu ☰) efface aussi les soins.

### 6.7 Revenus

Onglet secondaire (icône `pie`), accessible comme Santé via le bouton "⋯" (§6.6). Répartit les revenus entre **Moi** et **Ma femme** (clés internes `moi`/`conjoint`, libellés `REV_PERSON_LABEL`) avec des corrections de transfert entre les deux — pas de bouton flottant, pas de floutBar.

#### 6.7.1 Modèle
```
Store.settings.revenus = {
  periodFrom, periodTo,     // "AAAA-MM", filtre de période (mois calculé, cf. 6.7.5)
  groupFilter: [],          // noms de groupe/groupe de groupe (cf. 6.7.5)
  groupsExpanded,           // "Tout déplier" persistant, cf. 6.7.4
  moi:      { lines: [...lignes], transferOut: [...lignes], transferIn: [...lignes] },
  conjoint: { même forme }
}
```
Pas de regroupement par catégorie : `lines` est une liste **à plat**, directement sous "Avant transfert" (§6.7.2). Une **ligne** (`{id, type, label, sign, ...}`) est de l'un de ces trois types :
- **`manual`** : `values = {"AAAA-MM": montant}`, saisie libre.
- **`recurring`** : lit `AGG.buildRecurringIndex` (moteur de l'onglet Récurrent, §6.5) via `line.recurCategorie` + `line.recurLabel` — **portés par la ligne elle-même**, aucune catégorie parente n'existant plus pour les en déduire. C'est ce qui permet à une ligne récurrente de vivre aussi bien dans `lines` que dans un bucket de transfert (§6.7.3).
- **`budgetSalary`** : ne stocke aucun montant — lit/écrit **en direct** `Store.settings.budget.salaryEntries[AAAA-MM].femme` (le champ "Ma femme" du salaire, §6.3) : synchronisation bidirectionnelle automatique avec l'onglet Budget sans copie de donnée. Proposée uniquement sous **Ma femme** (`hasBudgetSalaryLine` limite à une seule instance sur l'ensemble de sa configuration), jamais sous Moi.

`sign` (`+1`/`-1`, défaut `+1`) : multiplicateur appliqué aux deux points d'entrée de lecture (`revLineColValue`/`revLineTotalValue`) — sert surtout à une ligne récurrente dont le montant, tel qu'enregistré côté transactions (ex. classé en Dépense), doit compter en sens inverse ici, sans toucher aux transactions sources. Réglable pour les trois types de ligne (bouton `±` dans la sheet de gestion, §6.7.6). **Aucun signe structurel n'est imposé par le bucket** (§6.7.3) : une ligne de `transferOut` prend `-1` par défaut à sa création, une ligne de `transferIn` prend `+1` — mais ce n'est qu'une valeur de départ, modifiable comme n'importe quelle autre ligne.

#### 6.7.2 Trois blocs et hiérarchie visuelle
Par personne, trois totaux dans cet ordre : **Avant transfert** (somme de `lines`, à plat) → **Transfert** (addition pure **Vers + Depuis**, jamais une soustraction — cf. §6.7.3, coloré selon le signe) → total final de la personne (porté par la **ligne Personne elle-même** — pas de ligne "Après transfert" séparée, retirée car strictement redondante avec ce total).

Format compact façon Récurrent (§6.5), **sans cascade d'indentation** : la ligne Personne (0 indentation, `.rev-person-row`) est le seul niveau distinct — "Avant transfert", "Transfert" et ses deux sous-blocs "Vers X"/"Depuis X" partagent tous **la même indentation** (22px, `.rev-cat-row`) ; les lignes de `lines` (feuilles, montants) apparaissent **directement** sous "Avant transfert", sans niveau de catégorie intermédiaire, à cette même indentation unique. Les libellés longs passent à la ligne (`white-space:normal` sur `.evo-col-label`, §12) plutôt que d'être tronqués — comportement désormais partagé par Évolution/Récurrent/Budget, cf. §12.

Repliage à deux `Set` module-locaux non persistés (même convention qu'Évolution/Récurrent) : `revCollapsedPersons` (clé = `moi`/`conjoint`) et `revCollapsedSections` (clés `"perso::avant"`, `"perso::transfert"`, `"perso::transfert::transferOut|transferIn"` — plus de sous-clé par catégorie, ce niveau ayant disparu). **Toute nouvelle sorte de ligne repliable doit porter la classe `.hidden` sur son `<tr>`** — la règle CSS est désormais générique (`.evo-table tr.hidden{display:none;}`, §12) après un bug où elle ne visait que `.evo-item-row.hidden` et laissait visibles les sections intermédiaires repliées.

#### 6.7.3 Transferts — addition signée, miroir automatique
`transferOut`/`transferIn` sont deux buckets **fixes** par personne (ni renommables ni supprimables) : `moi.transferOut` (argent envoyé) est le miroir exact de `conjoint.transferIn` (argent reçu), et vice-versa (`revMirrorOf`). Les deux lignes miroir partagent le **même `id`** — pas de table de correspondance séparée.

**"Transfert" = `transferOut` + `transferIn`, addition simple, jamais une soustraction dans le code** (`revPersonTransferColValue`/`TotalValue`) : aucun signe structurel n'est imposé par le bucket lui-même — chaque ligne compte pour sa valeur affichée telle quelle (montant × son propre `sign`, §6.7.1). C'est le **signe de la ligne**, pas une convention cachée de calcul, qui détermine si elle réduit ou augmente le total. Une nouvelle ligne de `transferOut` prend `-1` par défaut (une sortie d'argent réduit le total), une nouvelle ligne de `transferIn` prend `+1` — visibles et modifiables via le bouton `±` (§6.7.6), jamais figés.

**Le miroir recopie le signe INVERSÉ, pas à l'identique** (`revSyncTransferLineToMirror` : `mLine.sign = -revLineSign(line)`) — libellé, montants (ou lien récurrent) et type sont recopiés tels quels, seul le signe s'inverse d'un côté à l'autre. C'est ce qui fait qu'un même transfert réduit toujours le total de qui l'envoie et augmente celui de qui le reçoit, quel que soit le signe choisi sur la ligne d'origine (basculer le signe d'un côté fait basculer l'autre à l'inverse, sur toute modification ultérieure aussi). Toute création/renommage/changement de signe/édition de montant sur une ligne est répercutée sur sa miroir (`revSyncTransferLineToMirror`, y compris le lien récurrent le cas échéant) ; la suppression (`revRemoveTransferLineAndMirror`) retire les deux à la fois, avec confirmation nommant l'autre personne.

Une ligne de transfert peut être manuelle **ou** récurrente (jamais salaire synchronisé) — le choix récurrent passe par `pickRecurringTransaction(onPick)`, partagé avec l'ajout d'une ligne "Avant transfert" (§6.7.6) : depuis la suppression du niveau "Catégorie", plus aucun appelant n'a de catégorie déjà connue à l'avance, la fonction demande donc toujours d'abord la catégorie récurrente source, puis l'élément.

**Attention pour toute configuration antérieure à ce correctif** : une ligne de transfert créée avant l'introduction du signe inversé au miroir portait `sign:+1` des deux côtés (et le sens venait alors d'un multiplicateur structurel par bucket, depuis supprimé) — son total affiché change avec cette version ; il faut rebasculer son signe manuellement (`±`, §6.7.6) pour retrouver le comportement voulu.

#### 6.7.4 Colonnes, drill-down et édition
Même principe qu'Évolution (§6.4.3) : Total + une colonne par **année** de la période configurée par défaut (`revYearsList` — **toutes** les années de `[periodFrom, periodTo]`, y compris sans données, contrairement à Évolution qui n'affiche que les années réellement présentes), clic sur une année pour zoomer sur ses 12 mois, plus une colonne "lump" spéciale après décembre pour une année comportant une ligne récurrente à suffixe `AAAA` (même convention que Récurrent, §6.5). "Tout déplier/replier" (`#rev-expand-toggle`) : réglage global persistant (`groupsExpanded`), même mécanisme "dépassements individuels effacés au clic" que Transactions/Récurrent.

Cellules éditables (`rev-editable`, soulignement en pointillés) : uniquement lignes manuelles/salaire synchronisé, jamais récurrentes. Clic sur un **mois** (vue zoomée) → `openRevValueEditor`, éditeur compact à un champ (réutilise `PICKER.openInlineEditor`). Clic sur une **année** (vue non zoomée) → `openRevYearEditor`, nouvelle modale listant les 12 mois de l'année avec un champ chacun (réutilise `overlay-confirm`/`modal-confirm`, même esprit que l'éditeur de salaire du Budget, §6.3) — remplit plusieurs mois d'un coup sans avoir à zoomer puis toucher chaque cellule. Les deux écritures répercutent le miroir si la ligne éditée vit dans `transferOut`/`transferIn`.

#### 6.7.5 Filtres
**Période** (`periodFrom`/`periodTo`, deux `<input type="month">`) : même mécanique et même calcul de valeur par défaut que Récurrent (`ensureRevenusPeriod`, période la plus large couvrant transactions récurrentes + montants manuels déjà saisis + salaire Ma femme déjà renseigné côté Budget).

**Groupe** (`openRevFilterSheet`) : présenté **comme le filtre Groupe habituel de l'app** — groupé par groupe de groupe via `AGG.groupeHierarchyChrono`, ordre chronologique défini (§2.1 bis), sélectionnable au niveau du groupe de groupe (en-tête) ou d'un groupe précis, avec recherche. Implémentation propre à l'onglet (pas `NESTED_DIM_CONFIG`/`nestedFilterHtml`, qui sont couplés à l'état de filtre global `F`), mais même moteur de hiérarchie et mêmes classes CSS (`.groupe-section`/`.groupe-section-head`/`.groupe-child-item`). Stocké dans `groupFilter` (tableau de noms, mélange groupe de base et groupe de groupe). Ne s'applique qu'aux lignes récurrentes (les lignes manuelles/salaire synchronisé n'ont pas de transaction source) : `AGG.buildRecurringIndex(periodFrom, periodTo, groupFilter)` a gagné un 3ᵉ paramètre optionnel qui teste `t.groupeBase` **et** `getGroupeDisplay(t)` (résolution groupe de groupe, §2.2) — même sémantique à deux niveaux que le filtre Groupe de Transactions (§2.3), rétrocompatible (l'appel existant de Récurrent, §6.5, omet ce paramètre et n'est pas affecté).

#### 6.7.6 Gestion (sheet "Gérer mes revenus")
`overlay-revmgr`/`sheet-revmgr` (`openRevManager`) : bascule Moi/Ma femme, puis **une seule carte "Avant transfert"** (`avantLinesCardHtml`) listant toutes les lignes de la personne à plat (par ligne : signe `±` / réordonner ↕ / renommer ✎ **[manuel uniquement]** / supprimer) avec **"+ Ajouter une ligne"** (choix Manuel/Récurrent/**Salaire synchronisé (Budget)** si sous Ma femme et pas déjà présent) — plus de carte par catégorie, plus de "+ Ajouter une catégorie" ni de réordonnancement de catégories, ce niveau ayant été supprimé. Puis deux cartes fixes "Transferts" (Vers X / Depuis X, jamais réordonnables entre elles) avec leurs propres lignes (mêmes actions, mirées, sans option Salaire synchronisé) et leur propre "+ Ajouter une ligne" (`openAddTransferLineChoice`, Manuel/Récurrent uniquement). `overlay-revmgr`/`overlay-revfilter` sont placés **avant** `overlay-picker` dans le shell (§12) — tous les overlays partageant le même `z-index`, un picker ouvert depuis l'une de ces sheets doit rester au-dessus dans l'ordre du DOM.

#### 6.7.7 Export / import
Comme tous les autres réglages (§7.2), `revenus` est un champ de plus dans le même payload `params` unique — `window.__SF_REVENUS.buildParamsPayloadPart()`/`applyParamsImportPart(revenus, mode)` branchés sur `buildParamsPayload()`/`applyParamsImport()`. **Deux feuilles Excel dédiées** (§7, §8) :

| Feuille | Colonnes | Alimente |
|---|---|---|
| **Revenus_Lignes** | `Personne · Catégorie · Ligne · Type · Catégorie récurrente · Signe` | lignes des deux personnes, dans l'ordre d'apparition dans la feuille (pas de colonne Ordre, même convention que les autres listes, §7) |
| **Revenus_Montants** | `Personne · Catégorie · Ligne · Mois · Montant` | montants des lignes **manuelles uniquement** (récurrent et salaire synchronisé ne stockent rien, recalculés à l'import) |

**Volontairement deux onglets séparés, jamais fusionnés en un seul** : les deux feuilles ont des cardinalités différentes (une ligne par ligne définie vs une ligne par mois renseigné) et un onglet combiné aurait nécessité soit des colonnes dupliquées (`Personne`/`Catégorie`/`Ligne` identiques dans les deux blocs — ambigu pour Excel lui-même et fragile à toute édition manuelle : insertion/suppression de colonne, tri, qui décale silencieusement une lecture par position), soit une lecture par position plutôt que par nom d'en-tête (moins robuste). Lues par nom, comme le reste de la feuille Paramètres.

**`Revenus_Reglages` (période `periodFrom`/`periodTo` + `groupFilter`) a été retirée de l'Excel** — ces trois champs ne voyagent plus que via la sauvegarde `.json` ou la synchro Gist (§7.2, §8) ; un import Excel ne les touche jamais (`groupFilter` conserve un garde-fou contre un tableau vide qui écraserait un filtre existant, cf. `applyParamsImportPart` — un tableau vide `[]` est "truthy" en JS, la simple présence de la clé ne suffit pas à décider s'il faut l'adopter).

**Colonne "Catégorie" conservée uniquement pour les sentinelles de transfert** — depuis la suppression du niveau "Catégorie", une ligne normale (destinée à `lines`) l'exporte **vide** ; seules les deux sentinelles réservées (`"(Transfert - vers)"`/`"(Transfert - depuis)"`, jamais un nom de catégorie réel) y ont encore un sens, pour router une ligne vers `transferOut`/`transferIn` plutôt que vers `lines` à l'import. **Rétrocompatibilité** : un classeur exporté *avant* ce changement, avec un vrai nom de catégorie dans cette colonne pour une ligne normale, s'importe toujours correctement — la valeur est simplement ignorée (aucun regroupement recréé), la ligne rejoint `lines` comme n'importe quelle autre.

**Fusion (mode "Ajouter")** : le bloc `revenus` complet (les deux personnes ensemble) suit la famille "adoption non destructive" (§7.2, famille 2) — adopté uniquement si **rien n'est encore configuré localement pour aucune des deux personnes** (`lines` + les deux buckets de transfert, tous vides), jamais fusionné champ par champ ni partiellement écrasé. En mode "Remplacer" depuis Excel, gaté par `sheetsPresent.revenus` (import ciblé par onglet, §7.2) — un classeur ne contenant que, par exemple, `Budget` ne vide jamais une configuration Revenus existante. Une sauvegarde `.json`/synchro Gist (pas de notion de `sheetsPresent`) applique toujours le remplacement si la clé `revenus` est présente.

## 7. Import

- Formats : `.xlsx`/`.xls`, `.csv` (données), `.json` (sauvegarde propre, v2). Colonnes de données (Date/Type/Montant) : formats acceptés détaillés en §1.1.
- `findDataSheetName()` détecte la feuille de données via ses en-têtes Date+Montant (ignore "Paramètres").
- **Six feuilles optionnelles**, indépendantes les unes des autres (aucune n'est requise), lisibles depuis un classeur Excel de paramètres — **toutes alimentent `params`, retourné par `parseParametresSheet(wb)` avec exactement la même forme que `buildParamsPayload()` (§7.2)**, donc consommées par le même `applyParamsImport(params, mode)` que la sauvegarde `.json`/la synchro Gist, fusion ou remplacement compris. Ce nombre a été volontairement réduit (de treize à six) dans une passe de simplification : `Budget_Reglages`, `Budget_Comparaison`, `Reglages_Generaux`, `Comptes_Soldes_Perso`, `Evolution_Reglages`, `Evolution_Fusions` et `Revenus_Reglages` ont été retirés de l'Excel — les réglages qu'ils portaient ne voyagent plus que via la sauvegarde `.json` ou la synchro Gist (liste complète et raison d'être en §7.2) :

| Feuille | Colonnes | Alimente |
|---|---|---|
| **Paramètres** | `Groupe · Groupe de groupe · Type budget (Quotidien/Voyage) · Mois voyage · Date début (jours) · Date fin (jours) · [col. vide] · Compte · Type de compte · Acronyme · [col. vide] · Personne · Groupe de personnes · [col. vide] · Catégorie (classement forcé) · Type forcé (Revenus/Dépenses)` | `groupAliasRules`, `personAliasRules`, `accountTypes`, `accountAcronyms`, `groupKind`/`groupVoyageMonth`, `categoryTypeOverride`, `groupDateRange` |
| **Budget** | `Mois · Groupe · Catégorie · Montant · Remarque · Amorti (Oui/Non) · Vue (Perso/Couple/Les deux) · Vue uniquement (Oui/Non)` | `budget.adjustments` |
| **Budget_Salaires** | `Mois · Moi · Ma femme` | `budget.salaryEntries` |
| **Budget_Predefini** | `Clé · Groupe · Catégorie · Montant mensuel · Vue (Amorti/Réel/Les deux)` | `budget.compare.{predefined,predefinedVue}` |
| **Revenus_Lignes** / **Revenus_Montants** | voir §6.7.7 | `revenus.{moi,conjoint}` |

Trois colonnes vides intercalées dans **Paramètres** (après "Date fin (jours)", après "Acronyme", après "Groupe de personnes") — purement visuelles, pour séparer les blocs de colonnes contigus à la lecture dans Excel ; ignorées à l'import (ni lues ni requises), sans effet sur le mapping par nom des autres colonnes.

**Colonne "Mois voyage"** : vraie date Excel (toujours le 1ᵉʳ du mois, affichée `dd/mm/yyyy`), voir §8 pour l'écriture. Ancien en-tête `Mois voyage (AAAA-MM)` et ancienne valeur texte `AAAA-MM` : repli de lecture retiré (n'était plus nécessaire, la sauvegarde de l'utilisateur ayant été ré-exportée au format actuel) — un classeur antérieur à ce changement doit être régénéré avant réimport.

**Colonne "Groupe" de la feuille Paramètres — un seul bloc de colonnes contiguës** (au lieu de plusieurs blocs disjoints ailleurs dans la feuille dans une version antérieure) : `Groupe`, `Groupe de groupe`, `Type budget`, `Mois voyage`, `Date début/fin (jours)` se suivent directement. La colonne "Groupe" contient **toujours le libellé complet exact** (suffixe de date inclus) — sauf pour une règle générique volontairement créée sans occurrence précise (§2.1), auquel cas elle montre simplement le nom tel quel, sans suffixe puisqu'il n'y en a pas. **Détection automatique rétrocompatible** : si la valeur de "Groupe" contient elle-même un suffixe entre parenthèses (signe qu'elle porte le libellé complet, cas normal), le nom de base est dérivé automatiquement (`U.baseGroupe`) et la règle est traitée comme scopée à cette occurrence précise (`rule.full = valeur brute`) — sans cette détection, un ancien export où "Groupe" contenait déjà le libellé complet perdait silencieusement la quasi-totalité de ses règles de groupe de groupe à la ré-importation (le libellé complet ne correspondant à aucun nom de base connu). Type budget/Mois voyage/Bornes (jours) sont, eux, toujours indexés directement sur la valeur brute de "Groupe" (jamais dérivés), cohérent avec §2.1.

**Bug corrigé (ambiguïté jour/mois sur une date Excel "format intégré")** : `parseParametresSheet` lisait "Mois voyage"/"Date début (jours)"/"Date fin (jours)" via `sheet_to_json(..., {raw:false})`, c'est-à-dire le texte affiché de la cellule plutôt que sa vraie valeur. Pour une cellule au format personnalisé `dd/mm/yyyy` écrit par cette appli (§8), ce texte est fiable. Mais si la cellule porte le format Excel **intégré** "court" à la place (par ex. après une modification manuelle dans Excel, qui réapplique volontiers ce format par défaut à une date tapée à la main) — ce format n'a pas de représentation fixe, Excel l'affichant selon la locale de la machine, mais SheetJS (qui ignore cette locale) le formate toujours en anglais `m/d/yy` pour calculer ce texte, relu ensuite par `U.parseDateValue` en jour/mois (convention de toute l'appli, §1.1) : les deux ordres se contredisent. Sur "Mois voyage", où le jour vaut toujours 1, l'effet est uniforme et très visible : une date de juillet ("7/1/26") redevenait systématiquement le 1ᵉʳ janvier — **toutes les occurrences ayant ce format retombaient silencieusement en janvier de leur année**. Sur "Date début/fin (jours)", où le jour peut être n'importe quelle valeur, l'effet est plus sournois : correct par chance lorsque l'un des deux nombres dépasse 12 (l'ambiguïté est alors levée, y compris par le repli JavaScript natif en dernier recours dans `U.parseDateValue`), mais silencieusement jour/mois inversé sinon (ex. "4/7/18", écrit pour le 7 avril 2018, relu comme le 4 juillet) — 75 des 181 occurrences du fichier de test étaient concernées. Corrigé en lisant ces trois colonnes avec `raw:true` : `cellDates:true` étant déjà actif à la lecture du classeur, une cellule de type date est alors renvoyée comme un vrai objet `Date` (sans ambiguïté, quel que soit son format d'affichage) plutôt que comme du texte reformaté. Même correctif appliqué à la colonne `Date` de la feuille de transactions (§1.1) et à "Date du soin"/dates de remboursement de Santé (§6.6), qui lisaient leurs dates de la même façon.

**Ce correctif ne s'applique jamais à un import CSV** (`raw` reste `false` dans ce cas précis, sur les trois mêmes lectures) : SheetJS, en lisant un CSV, devine parfois lui-même — à tort, à l'anglo-saxonne mois/jour — qu'un texte `JJ/MM/AAAA` ambigu (jour ≤ 12) est une date, et c'est précisément la reformulation en texte (`raw:false`) de cette date mal devinée, relue ensuite par `U.parseDateValue` en jour/mois (sa convention par défaut, §1.1), qui annule cette erreur pour un CSV. Passer `raw:true` y aurait cassé la lecture (une date du 5 mars saisie `05/03/2026` aurait été comprise comme le 3 mai) : le texte brut tel que tapé reste donc la voie la plus sûre pour un fichier CSV, qui n'a de toute façon aucune notion de format de cellule.

### 7.1 Réconciliation (casse/accents + nouveaux éléments)

**Uniquement pour un import Excel/CSV avec des transactions déjà présentes** (jamais pour une restauration de sauvegarde `.json`, ni pour un premier import sur données vides — tout y serait "nouveau" par définition). Avant l'écran de résumé habituel, `DATA.buildReconciliation(txns)` compare chaque valeur importée (**Catégorie, Personne, Compte + Compte cible, Groupe** — pas Remarque, pas Type) aux valeurs déjà présentes dans `Store.transactions`, comparaison insensible casse/accents (`U.normalize`) :

- **Correspondance trouvée** (ex. "restauration" importé, "Restauration" existant) → alignement **automatique et silencieux** sur la casse existante, mutation directe de `txns` en place. Un message informatif ("N valeur(s) alignée(s)") apparaît sur l'écran de résumé, mais aucune confirmation n'est demandée.
- **Aucune correspondance** → valeur véritablement nouvelle. Si plusieurs variantes de casse d'une même valeur nouvelle coexistent dans le même import (ex. "Abonnements" et "ABONNEMENTS"), elles sont d'abord fusionnées entre elles (casse de la première occurrence rencontrée fait foi), puis présentées comme **une seule** entrée nouvelle.
- S'il existe au moins une valeur véritablement nouvelle, un écran dédié (`renderImportReconcile`) les liste, groupées par champ, chacune avec le nombre d'occurrences dans le fichier et deux choix : **"Nouveau"** (par défaut, créée telle quelle) ou **"Remplacer par…"** (ouvre le picker plein écran habituel, §6.2, pour la faire correspondre à une valeur déjà existante — faute de frappe, variante). Le bouton "Continuer" applique les choix aux transactions avant de passer à l'écran de résumé.

**Compte et Compte cible partagent un même espace de noms** : un compte existant côté source vaut aussi côté cible et inversement (un compte qui n'apparaît qu'en `compteCible` dans l'historique n'est jamais signalé comme nouveau si le même nom existe déjà en `compte`, et vice versa) ; une correspondance/un remplacement choisi s'applique aux deux champs à la fois.

**Santé (§6.6) a son propre flux d'import Excel/CSV, entièrement séparé** de tout ce qui précède — colonnes, dédoublonnage et écran dédiés, sans réconciliation casse/accents ; les soins ne transitent par ce §7 que de façon transparente lors d'une restauration `.json` complète (§6.6, §8).

- Choix à l'import : Transactions+Paramètres / Transactions seules / Paramètres seuls (comme à l'export, §8) ; l'onglet Santé, s'il est présent dans le classeur, est détecté et importé **indépendamment de ce choix** (même principe que pour une sauvegarde `.json`, §6.6/§8 — jamais gaté par la sélection Transactions/Paramètres). Puis Ajouter/Remplacer pour chaque volet (Transactions, Paramètres, Santé partage le mode choisi pour les Transactions). En mode Ajouter, `Budget_Salaires` fusionne mois par mois ; en mode Remplacer, tous les mois importés remplacent intégralement les saisies locales. `Budget_Predefini` suit la même logique.
- `Store.normalizeSettings()` est systématiquement rappelée en fin d'import de paramètres (import fichier ou synchronisation), pour migrer silencieusement tout réglage devenu obsolète (ex. un ancien mode Budget "Brut" retombe sur "Amort. + ajouts").

### 7.2 Ce qui voyage réellement dans "params" (`buildParamsPayload()` / `applyParamsImport()`)

**Un seul et même payload `params`**, quelle que soit la porte d'entrée — sauvegarde `.json` (§8), synchronisation Gist (§10), ou les feuilles Excel (§7 ci-dessus, `parseParametresSheet` construit un objet de forme identique, mêmes noms de champs). Toute correction ici s'applique donc automatiquement aux trois mécanismes à la fois, sans code dupliqué — **mais depuis la simplification de l'Excel (retrait de sept feuilles, cf. §7), l'Excel ne peuple plus qu'un sous-ensemble de ces champs** ; les champs qu'aucune feuille Excel restante ne porte sont simplement absents/`null`/vides dans l'objet retourné par `parseParametresSheet`, jamais activement écrasés (cf. "Ce qui ne voyage plus que par JSON/Gist" ci-dessous pour le détail et les garde-fous associés).

**Inclus** (correctif appliqué après un oubli constaté sur `customBalances`, `accountTypeOrder`, `budget.excludedAccounts` et `evolution.{merges,view,monthBasis}` — tous manquaient auparavant, silencieusement, des trois mécanismes) :
`groupAliasRules`, `personAliasRules`, `accountTypes`, `accountAcronyms`, `accountTypeOrder` (§6.1), `customBalances` (§6.1), `decimals` (§5), `groupKind`/`groupVoyageMonth`/`groupDateRange`, `categoryTypeOverride`, `budget.{adjustments,mode,scope,startMonth,endMonth,mainGroup,extraGroups,amortCategories,excludedAccounts,periodFrom,periodTo,salaryEntries,compare,mergeVoyages,mergeVoyagesGroups}` (`compare.predefinedVue` inclus au même titre que `compare.predefined`, §6.3.5), `evolution.{view,monthBasis,merges}` (§6.4.5), `revenus.*` (§6.7.7 — bloc à part, sa propre sémantique de fusion "tout ou rien" y est détaillée plutôt que dans la liste des trois familles ci-dessous).

**Ce qui ne voyage plus que par JSON/Gist depuis la simplification de l'Excel** (les sept feuilles retirées, §7) — l'Excel reste un moyen de transfert incrémental/manuel pour les transactions et les règles les plus fréquemment éditées à la main (groupes, comptes, budget mensuel), mais ces réglages, plus globaux et plus rarement modifiés, ne sont plus considérés comme devant transiter par un tableur :
- `budget.{mode,scope,startMonth,endMonth,mainGroup,extraGroups,amortCategories,excludedAccounts,periodFrom,periodTo}` — portés par l'ex-feuille `Budget_Reglages`, entièrement supprimée.
- `budget.compare.{enabled,mode,periodFrom,periodTo}` — ex-feuille `Budget_Comparaison`, supprimée (`budget.compare.predefined` reste porté par `Budget_Predefini`, feuille conservée, sans lien direct avec cette suppression).
- `accountTypeOrder` (§6.1), `decimals` (§5) — ex-feuille `Reglages_Generaux`, supprimée.
- `customBalances` (§6.1) — ex-feuille `Comptes_Soldes_Perso`, supprimée.
- `evolution.{view,monthBasis,merges}` (§6.4.5) — ex-feuilles `Evolution_Reglages`/`Evolution_Fusions`, supprimées.
- `revenus.{periodFrom,periodTo,groupFilter}` (§6.7.5, §6.7.7) — ex-feuille `Revenus_Reglages`, supprimée (`revenus.{moi,conjoint}`, les lignes/montants eux-mêmes, restent portés par `Revenus_Lignes`/`Revenus_Montants`, conservées).

**Deux correctifs anti-perte de données rendus nécessaires par ces suppressions**, tous deux dans le sens "l'absence d'un champ dans l'Excel ne doit jamais l'écraser à vide/`null` en réimportant" :
1. `applyParamsImport`, mode "Remplacer" : `budget.periodFrom`/`periodTo` reprennent désormais un repli sur la valeur déjà en place si l'import ne les fournit pas (`budgetSettings.periodFrom || Store.settings.budget.periodFrom`), même logique que `mode`/`scope` juste au-dessus — nécessaire uniquement en théorie depuis que `Budget_Reglages` (seule source Excel de ces champs) est entièrement supprimée, ce bloc n'étant plus jamais déclenché par un import Excel ; conservé par cohérence et en garde-fou pour toute réintroduction future.
2. `window.__SF_REVENUS.applyParamsImportPart` : `revenus.groupFilter` n'est adopté que si le tableau importé est **non vide** (`revenus.groupFilter && revenus.groupFilter.length`) — un tableau vide `[]` est "truthy" en JavaScript, un test de simple présence aurait donc vidé le filtre à chaque import Excel (qui, `Revenus_Reglages` disparue, fournit désormais toujours `groupFilter:[]`).

**Volontairement exclus** (état d'affichage/session courant, pas une donnée de configuration à préserver entre appareils — même principe que les filtres Transactions, `Store.settings.filters`, jamais synchronisés non plus) : `theme`, sélection de filtres courante (Transactions comme Santé, §6.6), `txnGroupsExpanded`/`recurrent.groupsExpanded`/`santeGroupsExpanded`, `budget.{detailView,monthlyView,displayMode}`, `recurrent.{periodFrom,periodTo}`, `evolution.cumulative` (§6.4.2 bis), `hideZeroAccounts` (§6.1). `Store.settings.sync` (jeton, ID de Gist) est exclu pour une raison différente et non négociable : **des identifiants ne doivent jamais se retrouver dans un fichier de sauvegarde ou repartir vers le Gist qu'ils servent à authentifier**.

**Sémantique de fusion (mode "Ajouter", tous mécanismes confondus)** — trois familles de comportement, jamais mélangées pour un même champ :
1. **Fusion par dédoublonnage** (listes de règles/entités identifiables individuellement) : `groupAliasRules`, `personAliasRules`, `budget.adjustments`, `evolution.merges.*` — chaque élément importé est ajouté sauf s'il existe déjà localement (`mergeRuleList`, clé de signature propre à chaque type de liste).
2. **Adoption non destructive** (réglage global unique, jamais fusionné champ à champ) : `accountTypeOrder`, `customBalances`, `budget.excludedAccounts`, la plupart des champs de `budgetSettings` — la valeur importée n'est adoptée **que si rien n'est encore configuré localement** ; elle n'écrase jamais un réglage déjà présent sur l'appareil qui importe.
3. **Jamais touché par un import "Ajouter"** : `evolution.view`/`evolution.monthBasis` (quelle vue est actuellement affichée) et `decimals` en mode fusion — seul un import "Remplacer" les modifie ; un "Ajouter" ne doit jamais changer silencieusement ce que l'utilisateur est en train de regarder.

**Mode "Remplacer" (`mode === "replace"`) : deux comportements distincts selon la porte d'entrée**, tous deux dans `applyParamsImport` :
- **Sauvegarde `.json` / synchro Gist** (`payload.params` n'a jamais de champ `sheetsPresent`, cf. `buildParamsPayload()`) : écrase **toujours tout** sans distinction, quel que soit le champ.
- **Import Excel ciblé par onglet** (`params.sheetsPresent` présent, cf. `parseParametresSheet()`) : chaque bloc de réglages n'est écrasé **que si la feuille Excel correspondante est effectivement présente** dans le classeur importé (`sheetsPresent.parametres`, `.budget`, `.revenus`) — un classeur ne contenant que, par exemple, `Budget` ne vide jamais `groupAliasRules`/`accountTypes`/etc. Les champs qui ne voyagent plus par aucune feuille Excel (liste ci-dessus : `accountTypeOrder`, `decimals`, `customBalances`, `evolution.merges`) ne sont, par construction, **jamais** écrasés par un import Excel — remplacer y est équivalent à ne pas y toucher, condition testée via `!params.sheetsPresent` (vrai uniquement pour JSON/Gist) plutôt que via un flag de feuille qui n'existe plus.

**Bug corrigé lors de la session de nettoyage post-simplification Excel** : ces conditions étaient auparavant écrites `if(sheetsPresent.parametres)`, `if(sheetsPresent.reglages_generaux)`, `if(sheetsPresent.comptes_soldes_perso)`, `if(sheetsPresent.evolution_fusions)`, `if(sheetsPresent.budget)` — des clés que `parseParametresSheet` ne renseigne plus du tout pour les trois dernières (feuilles supprimées) et qu'un payload JSON/Gist n'a **jamais** renseignées (`sheetsPresent` y est simplement absent, donc `{}`). Conséquence : une restauration `.json` ou une synchro Gist en mode "Remplacer" n'appliquait plus **jamais** `groupAliasRules`, `personAliasRules`, `accountTypes`, `accountAcronyms`, `groupKind`, `groupVoyageMonth`, `groupDateRange`, `categoryTypeOverride`, `accountTypeOrder`, `decimals`, `customBalances`, `budget.adjustments` ni `evolution.merges` — tous silencieusement ignorés, l'appareil de destination gardant ses valeurs locales au lieu de recevoir celles de la sauvegarde/du Gist. Corrigé en généralisant le garde-fou déjà utilisé pour `revenus` (`!params.sheetsPresent || sheetsPresent.xxx`) et en retirant les trois flags de feuille désormais inexistants au profit d'un simple `!params.sheetsPresent`.

## 8. Export
Menu → Excel (.xlsx) ou sauvegarde (.json).

**Export Excel — trois cases à cocher indépendantes (Transactions / Paramètres / Santé), 1 à 3 sélectionnables à la fois** (`openExportExcelScopeChoice`, remplace l'ancien choix exclusif à trois options) — la case Santé n'apparaît que si `Store.santeItems` n'est pas vide. Un seul classeur est produit, avec une feuille par volet coché (Transactions, les feuilles Paramètres de §7 pour ce volet, et/ou "Santé" — mêmes colonnes que l'export Santé dédié, §6.6). Nom de fichier : suffixe reflétant la sélection (`_transactions`, `_parametres`, `_sante`, ou combinaisons `_parametres_sante` etc.), aucun suffixe si les trois sont cochées. Export JSON (sauvegarde `.json`) : choix inchangé, exclusif à trois options Transactions+Paramètres / Transactions seules / Paramètres seuls — Santé, elle, voyage **toujours** avec le JSON quel que soit ce choix (§6.6), n'a donc jamais eu besoin d'une case dédiée sur ce mécanisme.

**Dates au format Excel natif JJ/MM/AAAA** : toutes les colonnes à précision jour sont écrites comme de vraies cellules de type date (`XLSX.utils.aoa_to_sheet(data, {cellDates:true})`), avec le format d'affichage forcé à `dd/mm/yyyy` (`setColumnDateFormatDDMMYYYY`). **"Mois voyage" (§2.4)** : vraie cellule date au 1ᵉʳ du mois (`voyageMonthToDateObj`, ex. mois interne `"2024-01"` → cellule affichée `01/01/2024`) ; le stockage interne (`Store.settings.groupVoyageMonth`) reste inchangé, seule la représentation Excel change. À l'import, `U.parseDateValue` lit indifféremment une vraie cellule date, un numéro de série Excel, ou du texte JJ/MM/AAAA(-AA), et n'en retient que l'année/le mois (le jour est toujours ignoré). L'ancien en-tête `Mois voyage (AAAA-MM)` et le repli texte `AAAA-MM` strict ont été retirés (plus nécessaires) : seule la colonne `Mois voyage` au format date actuel est lue.

**Colonne Type en français** : la feuille de transactions exporte `Revenu`/`Dépense`/`Transfert` (au lieu de l'anglais interne `Income`/`Expense`/`Transfer`), cohérent avec le format d'import (§1.1). Les montants restent des cellules numériques signées classiques — la virgule décimale à l'affichage est gérée par Excel selon sa locale, aucune conversion de format nécessaire côté export.

**Feuille `Budget_Predefini`** : colonne `Vue (Amorti/Réel/Les deux)` ajoutée (§6.3.5) — texte simple ("Amorti"/"Réel"/"Les deux"), absente ou toute valeur non reconnue relue comme "Les deux" à l'import (comportement historique, montant identique dans les deux vues).

**Santé (§6.6)** garde son export Excel dédié séparé (menu propre à l'onglet, colonnes identiques) **et** peut désormais aussi être incluse dans l'export Excel principal via la case à cocher ci-dessus (même fonction `buildSanteExportRows()` partagée par les deux chemins, pour ne pas dupliquer le mapping de colonnes) — les deux coexistent, ce n'est plus l'un ou l'autre. Toujours incluse dans la sauvegarde `.json` complète, quel que soit le périmètre Transactions/Paramètres choisi pour le JSON.

## 10. Synchronisation manuelle (GitHub Gist)

Mécanisme de transfert entre appareils alternatif à l'export/import de fichier, sans backend : sauvegarde/récupération du payload complet (transactions + paramètres + soins et réglages de l'onglet Santé, §6.6 — même format que la sauvegarde `.json` §7/§8) sur un Gist GitHub privé, via l'API `api.github.com/gists/{id}` appelée directement depuis le navigateur. Les soins Santé suivent la même règle "distant/local/hash" que les transactions ci-dessous, sans fusion possible à la récupération (remplacement complet).

**Configuration** (`Store.settings.sync = {token, gistId, filename, lastSyncedAt, lastSyncedHash}`) : jeton d'accès personnel (scope **`gist`** uniquement recommandé). L'**ID du Gist est optionnel** : laissé vide, le premier "Synchroniser" crée automatiquement un nouveau Gist secret et mémorise l'ID retourné.

**Synchroniser** (`smartSync`) : sens **automatique** dans les deux directions.
1. Calcule trois hash : local actuel, distant actuel, `lastSyncedHash`.
2. Seul le distant a changé → récupère automatiquement. Seul le local a changé → sauvegarde automatiquement. Identiques → rien à faire.
3. **Les deux ont changé indépendamment** → modale de conflit demandant explicitement "Garder cet appareil" ou "Utiliser le Gist".

**Forcer sauvegarde** / **Forcer récupération** : action à sens unique, pour un rattrapage manuel.

**Indicateur** (`#btn-sync`) : icône + couleur selon l'état (`computeStatus()`). Module `window.__SF_SYNC` : `{open, updateIndicator, pushToGist, pullFromGist, smartSync}`.

**Colonnes figées (tableau Évolution, §6.4.3, et Récurrent, §6.5)** : pattern réutilisable si un futur tableau a besoin du même comportement — `<table>` HTML classique (pas de grille CSS), `box-sizing:border-box` obligatoire sur toutes les cellules, largeurs `width`/`min-width`/`max-width` identiques sur chaque colonne figée, et `left` de la 2ᵉ colonne figée = largeur exacte de la 1ʳᵉ (Évolution fige Libellé + Total ; Récurrent ne fige que Libellé, sa colonne Total défile comme les autres, cf. §6.5). Défilement horizontal au-delà des colonnes figées : `U.enableDragScroll` (glisser-déposer souris + tactile natif, §6.4.3/§12), partagé par Évolution, Récurrent et la vue mensuelle du Budget. Un en-tête sticky "flottant" au-dessus d'une carte (§6.3.1) doit être un enfant direct du conteneur qui englobe tout le contenu à couvrir par le sticky, pas seulement de la carte elle-même.

**Pour ajouter une dimension similaire à Groupe/Personne** : dupliquer le schéma `getXDisplay`/`findXAliasRule`/`distinctBaseX`/`xHierarchy` dans le module Filtres+Agrégations, appeler `createAliasManager({...})`, ajouter une entrée `NESTED_DIM_CONFIG` pour le filtre imbriqué.

**Pour ajouter une dimension à l'onglet Évolution** : ajouter un cas dans `buildEvolutionIndex` (section/item pour cette dimension) et dans `txnMatchesDimTarget` (filtrage de la feuille de détail) — les deux doivent rester cohérents entre eux (même définition de "quelle transaction appartient à quel item/section").

**Pour un picker de fiche transaction groupé/trié différemment** (§6.2) : `renderPickerList` accepte `opts.hierarchy = {sections: Map, flat: [], preSorted?, selectableHeaders?, expandedByDefault?, kindFn?}` — sans `preSorted`, les sections et leurs enfants sont re-triés alphabétiquement par la fonction elle-même (comportement historique, toujours utilisé par le picker de groupe principal/additionnel du Budget, `groupPickerHierarchy`, §6.3.2) ; avec `preSorted:true`, l'ordre fourni par l'appelant est respecté tel quel (cas du tri chronologique des groupes, §2.1 bis — fiche transaction, filtre Groupe, et désormais aussi picker de groupe d'un ajustement §6.3.6 — et du picker Catégorie qui impose l'ordre Revenus puis Dépenses). `selectableHeaders:false` désactive la sélection de l'en-tête de section lui-même (utilisé par Catégorie, où l'en-tête est un type, pas une valeur valide) ; `expandedByDefault:true` déplie toutes les sections dès l'ouverture du picker ; `kindFn(base)` (optionnel, ex. icône Voyage/Vie quotidienne du picker d'ajustement §6.3.6) retourne un HTML à préfixer devant le libellé de chaque groupe précis — jamais devant un en-tête de section, un groupe de groupe pouvant mélanger plusieurs types.

**Pour ajouter un futur onglet secondaire derrière le bouton "⋯"** (§6.6, §11) : ajouter une entrée à `MORE_TABS`/`MORE_TAB_KEYS` (module Contrôleur), un nouveau `view-*` dans le shell, inclure le nouvel onglet dans `showFloat` si le bouton flottant s'applique, brancher `refreshCurrentTab()` et le dispatch des 4 boutons du bouton flottant selon `currentTab` — l'onglet Santé sert de modèle complet pour ce pattern, y compris pour une liste déroulante personnalisable avec ajout à la volée (`PICKER.openPicker({..., allowNew:true})` + persistance dans `Store.settings`) et un export/import Excel dédié (§6.6) qui reste distinct des écrans du flux principal (§7/§8) tout en partageant son mapping de colonnes (`buildSanteExportRows`) et sa fonction de lecture (`rowToSanteItem`), les deux étant désormais aussi mobilisées par le flux principal (case à cocher Santé à l'export §8, détection automatique de la feuille "Santé" à l'import §7).

## 13. Limites connues
- Pas de synchronisation automatique entre appareils : export/import JSON ou Excel, ou synchronisation manuelle GitHub Gist (§10), comme mécanismes de transfert. Résolution de conflit au hash global uniquement (pas de fusion champ par champ).
- Détection "Paramètres"/"Budget"/etc. et mapping de colonnes basés sur des noms d'en-tête normalisés, pas sur la position.
- Règles de groupe : résolution "occurrence précise d'abord, règle générique en repli" (§2.1), toujours manuelle (aucune déduction géographique/temporelle automatique). Il n'existe plus de fenêtre de dates sur les règles elles-mêmes (§2.5) — seule la présence/absence d'un libellé complet distingue les occurrences.
- `groupDateRange` est une donnée déclarative simple (aucune vérification de cohérence avec les dates réelles des transactions du groupe, hormis le garde-fou jours ≤ 0). La date de fin dynamique "aujourd'hui" (§2.5) ne s'applique qu'à `dateTo` ; il n'existe pas d'équivalent pour `dateFrom`.
- Onglet Évolution : les fusions de sections (§6.4.5) sont indépendantes par dimension et non partagées avec un quelconque mécanisme de groupe de groupe/personne — fusionner deux sections dans Évolution ne crée aucune règle `groupAliasRules`/`personAliasRules` et inversement. Depuis le retrait des boutons de fusion de l'interface, une nouvelle fusion ne peut plus être créée que via JSON/Gist (§7.2, l'Excel ne le permet plus depuis le retrait d'`Evolution_Fusions`) — l'onglet ne permet plus que d'en supprimer une existante.
- `evolution.cumulative` (§6.4.2 bis) et `hideZeroAccounts` (§6.1) sont des réglages locaux à l'appareil, volontairement absents de `buildParamsPayload` (§7.2) : un changement d'appareil réinitialise ces deux affichages à leur valeur par défaut, quel que soit le mécanisme de transfert. `evolution.view`/`monthBasis`/`merges`, eux, sont bien inclus dans `buildParamsPayload` et voyagent via la sauvegarde `.json` ou le Gist — mais plus via l'Excel depuis le retrait d'`Evolution_Reglages`/`Evolution_Fusions` (§7.2) : un classeur Excel ne peut donc plus être utilisé pour transférer la vue Évolution ou ses fusions de sections d'un appareil à l'autre, seul JSON/Gist le permettent désormais.
- `AGG.getGroupStartDate` (§2.1 bis) interprète le suffixe entre parenthèses d'un groupe (`AA-MM-JJ`/`AA-MM_MM`/`AA-MM`/`AAAA`) uniquement en repli, quand aucune date de début n'est configurée manuellement — un suffixe dans un format non reconnu (texte libre, etc.) retombe silencieusement sur la date de la transaction la plus ancienne du groupe, sans avertissement.
- Réconciliation d'import (§7.1) : ne couvre que Catégorie/Personne/Compte/Compte cible/Groupe — pas Remarque, pas Type. Ne s'exécute que pour un import Excel/CSV avec des transactions déjà présentes ; une restauration `.json` ne passe jamais par cette étape (les valeurs y sont supposées déjà cohérentes, issues d'un export de l'app elle-même).
- Onglet Santé (§6.6) : la fusion à l'import (Excel dédié, détection automatique dans un classeur du flux principal, ou sauvegarde `.json`) ignore silencieusement un soin dont l'id existe déjà — comme pour les transactions (§7), elle ne met jamais à jour un soin existant (ex. un `termine` basculé localement puis un import "Ajouter" du même fichier source ne l'écrase pas). Pas de réconciliation casse/accents comme en §7.1 sur son propre flux Excel dédié, ni sur la détection automatique côté flux principal.
- Le filtre Groupe de Santé partage les comptages du filtre Groupe des Transactions (§2.1 bis, §6.6) — un groupe peut donc apparaître avec un nombre qui ne correspond à aucun soin si aucun n'y est encore rattaché.
- Santé : pas de taux de change — `montantDevise` est un champ informatif indépendant de `montantEur`, jamais calculé ou converti automatiquement.
- Revenus (§6.7) : une ligne récurrente est reliée par `(recurCategorie, recurLabel)` — une catégorie et un nom de transaction sans date, exactement comme un item de l'onglet Récurrent (§6.5). Si la catégorie ou le texte de la Remarque change ensuite côté transactions, le lien cesse silencieusement de correspondre et la ligne affiche 0, sans avertissement. Le filtre Groupe de Revenus (§6.7.5) ne s'applique qu'aux lignes récurrentes ; il n'existe aucun moyen de restreindre une ligne manuelle ou salaire synchronisé à un groupe.
- Détection automatique de la feuille "Santé" dans le flux d'import principal (§7) : le mode Ajouter/Remplacer appliqué aux soins suit toujours celui choisi pour les **transactions** (`chosenMode`), même si le volet Transactions n'est pas importé (classeur ne contenant qu'un onglet Santé, ou volet décoché) — il n'existe pas de choix Ajouter/Remplacer dédié aux soins sur cet écran, contrairement à l'écran d'import Santé dédié (§6.6) qui, lui, propose son propre choix.
- Navigation précédent/suivant de la fiche transaction (§6.2) : la liste de navigation est figée à l'ouverture de la fiche et ne protège que le temps où celle-ci reste affichée — fermer la fiche puis rouvrir une transaction repart d'une liste recalculée sur le filtre à jour, dans laquelle une transaction ayant entre-temps quitté ce filtre n'apparaît plus. Aucune navigation n'est disponible pour les fiches ouvertes depuis un autre onglet (Budget, Récurrent, Évolution, Santé) — les flèches y sont absentes.
- Ajustements manuels du Budget (§6.3.6) : le champ Groupe peut désormais cibler n'importe quel groupe précis ou de groupe, mais la correspondance avec une carte reste une **égalité stricte de libellé** (`adj.groupe === cfg.mainGroup` ou un élément de `cfg.extraGroups`) — sans repli hiérarchique parent/enfant. Un ajustement sur un groupe de groupe n'est jamais repris automatiquement par une carte configurée sur l'un de ses groupes enfants (et inversement) : il faut que le champ Groupe de l'ajustement corresponde exactement au réglage de la carte visée.
- Testé via Playwright (Chromium headless) quand l'environnement le permet, sinon relecture manuelle systématique + `node --check` sur le script extrait ; SheetJS nécessite un accès internet au premier chargement.
